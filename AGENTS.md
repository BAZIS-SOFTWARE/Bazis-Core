# AGENTS.md

## Контекст проекта

Цель проекта - это создать полноценное независимое от клиентов (графических приложений) CAE ядро. 
Ядро строится на CAD ядре, которе в перспективе может быть переменным.

CAE ядро строиться на нескольких библиотеках:

- Вспомогательные геометрические сущности и операции над ними Geometry
- Сеточные сущности и операции над ними Model
- Видовое представление и операции с ним в классе ModelView
- Сущности граничных условий и свойства рассматриваемых сред и операции над ними Project
- Пре и пост процессор PreProc, PostProc
- Операционный контроллер OperationalController, который связывает сеточные сущности и операции над ними, сущности граничных условий и свойства рассматриваемых сред и операции над ними, геометрические операции и CAD ядро (сейчас OOC через GMSH.dll). Важно, что OperationalController предоставляет систему событий, для внешнего клиента (GUI), через которую сообщает об наступивших изменениях в данных.

SPH - сферический объемный источник тепла (sphear)
MRF - подвижная система координат (moving reference frame)
gmsh - геометрическое (CAD) ядро, позволяющее загружать CAD модели
проект TestModel не проверять на компиляцтю. Он устарел и не используется.

## Состав команды и зоны ответственности

* **@core-architect** (Проектировщик) — Отвечает за верхнеуровневую архитектуру ядра CAE, ООП-структуру и принципы SOLID (интерфейсы, классы, DTO)
* **@core-developer** (Разработчик) — Реализует алгоритмы построения сетки, квадратуры для вычисления объемов и площадей. Граничные условия и инструкции "решателю". Основной язык C# (.NET) строго по спецификациям и диаграммам от архитектора.
* **@core-tester** (Тестировщик) — Создает модульные тесты, тестирует CRUD функции, верифицирует расчеты с аналитическими решениями и ловит утечки памяти.

## Протокол взаимодействия и конвейер (Pipeline)

1. **Инициация**: При поступлении команды `/goal` оркестратор декомпозирует задачу и в первую очередь привлекает **@core-architect** для составления технического плана решения задачи. Если план согласован с оркестратором, он передается далее в разработку.
2. **Передача в разработку**: После того как оркестратор утверждает план работ, задача вместе с контекстом делегируется **@core-developer** для написания управляемого C# кода.
3. **Верификация**: Готовый код от разработчика отправляется к **@core-tester**. Субагент разворачивает тестовое окружение и запускает тесты.
4. **Обратная связь**: 
   - Если **@core-tester** находит баги, он возвращает задачу обратно к **@core-developer** с описанием ошибок.
   - Если тесты пройдены успешно, оркестратор объединяет код и предлагает оформить (или изменить) документацию.
5. Если принято решение оформить (или изменить) документацию, то вызывается **@core-architect**, который готовит документацию (диаграммы, пояснения и спецификации). Когда они готовы **@core-architect-helper**, готовит итоговый документ или обновляет его. 

После этого оркестратор  завершает выполнение глобальной цели.

## Правила кодирования
- Стараться не использовать глобальные переменные
- Явно не типизировать переменные, там где это не нужно
- При написании кода старайся не использовать явную типизацию переменных. 
- Не пиши входные данные у методов столбиком, с переносом строки. 
- Старайся не использовать понижающее приведение типов (downcasting).Только в крайнем случае, когда без этого никак. 
- Придерживайся принципов SOLID и ООП.
- Старайся не создавать статических классов и методов, только если без этого никак (например от этого зависит производительность в сильно нагруженном месте)
- Старайся не использовать вызов метода для получения входных данных внутри круглых скобок другого метода.
- Если методы возвращают коллекции объектов, старайся использовать "ленивые методы" yield return. Полученные методы используй в цикле ForEach
- Старайся не использовать кортежи для возврата значений методов.
- Если используешь LINQ, то не делай длинные цепочки методов. Максимум 3.
- Не создавай методы в классах под атомарные операции не получив явного разрешения.

## Правила проектирования
- Придерживайся принципов SOLID и ООП.
- используй в качестве справки при решении архитектурных вопросов источник swebok-v3.pdf в папке Info
- При проектировании классов старайся не дублировать ссылки на существующие объекты.
- Не создавай методы в классах под атомарные операции не получив явного разрешения.
- Не планируй вызывать события в горячих (нагруженных) циклах - больших коллекциях, чтобы не порождать огромное кол-во однотипных сообщений

## Правила документирования
При изменении кодовой базы компонентов следует создвать диаграммы классов для проектов входящих в решение, кроме тестовых.

Если проект ссылается на другой проект и использует его структуры данных, то не следует подробно описывать структуры подключаемого проекта, а лишь разместить точку входа для этих структур (метод, перечисление и т.д.) на диаграмме.

Для интерфейсов на диаграмме необходимо показывать состав: методов, событий, свойств.

Для классов на диаграмме необходимо показывать используемые методы, события. Если класс реализует интерфейс, то дублировать информацию не требуется, а нужно только добавлять те методы, которых нет в наследуемом интерфейсе.

Не нужно строить диаграммы для исключенный из проекта файлов, где храняться классы и прочие структуры данных.

После подготовки диаграмм mdpulm нужно проверить помещается ли диаграмма в область рендера. Если нет, то ее следует разбить на несколько диаграмм. 
Каждая поддиаграмма называется также как материнская, но с приставкой в виде цифры.
Вынесенные на поддиаграммы компоненты следует помечать на материнской и указывать место их расположения (название поддиаграммы). На диаграммах должны быть ссылки друг на друга, чтобы можно было осуществлять навигацию.

В итоге для каждого проекта готовится единый многостраничный pdf, где собираются все диаграммы кроме тестовых проектов. Ссылки, используемые для навигации, на диаграммах должны поддерживаться в pdf документе и по клику открывать страницу на которой расположена искомая диаграмма.

Например: для проекта Model создается Model.mdpuml, Model-1.mdpuml, Model-2.mdpuml и т.д. Model и Model-1 расположены на разных страницах итогового pdf. На странице с Model есть указание в виде ссылки на Model-1. По клику на ссылку должен произойти переход на страницу с Model-1.

## Правила тестирования
- В проекте тестов, должны быть тесты для каждого проекта.
- Тесты каждого проекта должны быть в отдельной папке.
- Пространство имен для тестов в папках формируется по правилу: имя_проекта_test.имя_папки 
- Тестами должны покрываться основные методы,свойства классов.


## Устойчивые интеграционные правила
Так как у нас мультифизика, то данные - правила, которыми обмениваются задачи, также приведены в соответсвие принятой стратегии.
Под данными понимаются физические поля. На таблице ниже показано какие поля принимают и отдают физические задачи.

Сведения о полях хранит класс GeneralParameters:

ТЕПЛОВАЯ ЗАДАЧА
├── Родные поля: T,ph(x, t)                 		→ набор "Термический"
└── Неродные поля: v,p,T(x, t)|C,T(x, t)      		→ наборы "Гидродинамический"|"Химический"

МЕХАНИКА
├── Родные поля: u,σ,ε,T,ph(x, t)           		→ набор "Механический"
└── Неродные поля: T,ph(x, t)|C,T(x, t)|v,p,T(x, t)   → набор "Термический"|"Химический"|"Гидродинамический"

ГИДРОДИНАМИКА
├── Родные поля: v,p,T(x, t)                  		→ набор "Гидродинамический"
└── Неродные поля: T,ph(x, t)                       → набор "Термический"

ФИЗХИМИЯ
├── Родные поля: C,T(x, t)                  		→ набор "Химический"
└── Неродные поля: T,ph(x, t)                       → набор "Термический"

где x - координата, t - время

Схема данных для хранения отдельно взятого поля:

Поле
├── Название: Набор
└── Источник: Файл / Значения

Если "Файл"
└── Файл: Путь

Если "Значения"
├── Группа: Значения (Записываются через запятую)
├── Группа: Значения (Записываются через запятую)
и.т.д.

Можно использовать любую группу, чтобы задать поле. Группа может быть узловой или элементной.

По-умолчанию при связывании задач препроцессор PreProc пишет начальные условия для групп элементов, состоящих в MatData

Набор это - Термический,Механический,Химический,Гидродинамический

Значения - описывает физические поля и их постоянные величины в зависимости от типа (векторное/скалярное). Значения составляют цепочки значений, разделенных запятой. Например : Значения - Значение,Значение,Значение...

Каждое "Значение" в этой цепочке - это физическое поле и его величина. Ниже используемые в расчетах поля:

Поля заданные в формате (Поле Величина):
T value - температура
ph value,value,value и т.д. (зависит от фазового состава материала)
v value,value,value (зависит от размерности задачи) - скорость
u value,value,value (зависит от размерности задачи) - перемещения
p value - давление
C value - концентрация
σ value,value,value,... (это тензор и зависит от размерности задачи) - напряжение
ε value,value,value,... (это тензор и зависит от размерности задачи) - деформация

Правила записи тензоров
XX,YY,ZZ,XY,XZ,YZ - 3д случай
XX,YY,ZZ,XY - 2д осисимметрия случай
XX,YY,XY - 2д случай
XX - 1д случай

Если для выбранного набора не все величины перечисленны, значит они равняются нулю.Если ничего не записано, значит все равны нулю.
Если в поле значение написано ноль - это является ошибкой.
То есть одиночный 0 недопустим, а T 0 и v 0,0,0 допустимы.

Например для механики - Группа : T value,ph value,value,value,value,value
Например для гидродинамики - Группа : v value,value,value,p value
