# ModelView: разделение модели и представления

Пояснение к `ModelView.mdpuml`. Диаграмма держит структуру, этот файл — решения
и их причины.

**Правило для диаграммы:** в тексте заметок не должно быть угловых скобок, кроме
`<b>`. Просмотрщик принимает `<int,int>` за неизвестный HTML-тег и отказывается
открывать файл — синтаксис при этом безупречен, PlantUML рисует такой файл без
единого предупреждения. В телах классов скобки безопасны, ломаются только
заметки. Понадобилось назвать обобщённый тип в заметке — пишите словами.
Заодно держите картинку уже 4096 px: при превышении PlantUML молча обрезает её
по лимиту канвы. Поэтому обоснование живёт здесь, а не в заметках.

## Задача

Скрытость и выделение объектов жили в самих объектах модели (`Color`,
`ViewState` в `IModelObject`) и вычислялись через цвет: «выделено» означало
«цвет равен `SelectObjectColor`» — 19 мест в GUI. Отсюда потеря выделения при
смене прозрачности (`MainMenuEvents.cs:107-109`) и пять разбросанных вызовов
`SetBackColorToAllObjects()` вместо одного уведомления.

`Color` и `ViewState` из `IModelObject` в коде уже убраны. Остаток цвета в
`Model` — на наборах, см. раздел «Цвет уходит из Model целиком».

Состояние вида выносится из модели в `IModelView`. Модель не знает о
представлении, представление знает о модели.

## Единица хранения — тип, а не объект

`ModelView` хранит один словарь `ObjType -> IObjectsView`. `IObjectsView` —
состояние вида объектов одного типа, внутри два разреженных множества номеров.

Рассматривался вариант `ObjType -> List<ViewObject>`, где `ViewObject` держит
признаки одного объекта. Отклонён:

1. **Поиск.** `GetVisible` и `GetColor` вызываются на каждый объект при сборке
   вершинных буферов. Множество номеров отвечает за O(1), список — за O(n)
   на каждый объект.
2. **Память.** Хранятся только исключения — скрытые и выделенные. Объект на
   запись это заголовок плюс поля вместо 4 байт номера.
3. **Состояние по умолчанию.** У разреженного множества «записи нет» означает
   «видим и не выделен» — структурная гарантия. С `ViewObject` запись надо
   создавать при первом признаке и удалять, когда все признаки вернулись к
   умолчанию, иначе коллекция растёт монотонно. Инвариант вместо гарантии.
4. **Параллельный граф.** `ViewObject` со ссылкой на `IModelObject` дублирует
   модель и расходится с ней при удалении и перенумерации — возврат к
   `ViewState` внутри объекта, от которого и уходим.

Новый признак вида (наведение, блокировка, локальный цвет) добавляется полем
внутри `ObjectsView`, а не новым словарём в `ModelView`: два словаря при N
признаках превращаются в N словарей, и про `Prune` надо помнить в каждом.

Словаря переопределений цвета нет. Все записи цвета в отдельный объект в GUI —
это либо выделение (`-> SelectionColor`), либо раскраска по виду условия
(`CheckCondData.cs:52-58`), а это функция от данных задачи и режима раскраски,
а не хранимое состояние.

Порядок выделения не хранится: сегодня его и так нет — `CreatePlot.cs:53`
перебирает всю модель и фильтрует по цвету. Упорядоченное выделение — отдельная
будущая функция.

## Ключ — (ObjType, Number)

Номера не уникальны между типами: узел N5 и элемент N5 — разные объекты.
Поэтому `ObjType` выбирает `IObjectsView`, а `Number` ищется внутри него.

## Разрешение цвета в GetColor

1. объект выделен → `SelectionColor`
2. иначе → цвет набора из стилей `ObjectsView` (см. раздел про вынос цвета)
3. к результату применяется `Transparency` (альфа)

Пункт 1 убирает нынешнее «выделено == цвет равен `SelectObjectColor`» и чинит
потерю выделения при смене прозрачности.

### Кто знает, в каком объект наборе

Вид не знает и знать не должен. Принадлежность объекта набору — это данные
задачи (наборы элементов это части конструкции, материалы), и живёт она в
модели: `IObjectsData.GetSetInfo(ObjType, int)`. `ObjectsView` хранит только
соответствие «имя набора → стиль».

**Но спрашивать это на каждый объект нельзя.** Реализация для элементов такая:

```csharp
E1DCollection.Select(x => x.Value).FirstOrDefault(x => x.ContainsKey(objNumber));
```

Линейный перебор наборов, в каждом `ContainsKey`, плюс аллокации LINQ — и всё
это на каждый вызов. Если сборка буферов будет звать `GetColor(ObjType, int)`
поштучно, получится O(объекты × наборы) и куча мусора на кадр.

Для точек, кривых, поверхностей и узлов набор ровно один на тип
(`PointsSet`, `CurveSet`, `SurfaceSet`, `NodesSet`), так что проблема касается
только элементов — но именно их в модели больше всего.

### Сборка буферов идёт по наборам

Разворачиваем цикл наизнанку: снаружи наборы, внутри их объекты.

```csharp
foreach (var setInfo in objects.GetSetsInfo(type))
{
    var mode = view.GetViewMode(setInfo);
    var visible = new List<IModelObject>();
    var colors = new List<Color>();
    foreach (var number in setInfo.GetNumbers())
    {
        if (!view.GetVisible(type, number))
            continue;
        visible.Add(objects.Find(type, number));
        colors.Add(view.GetColor(setInfo, number));
    }
    ...
}
```

Набор разрешается один раз на набор, а не на объект: `GetColor(ISetInfo, int)`
уже знает цвет набора, поэтому на объект остаются два поиска числа в множестве.
Медленного `GetSetInfo(objType, number)` с перебором наборов в горячем цикле
нет. Что делают с этими двумя списками дальше — в разделе «Что получает
презентер».

Это и естественный порядок для отрисовки: буфер всё равно нарезается по наборам
и режимам (`ViewMode`), так что снаружи цикла оказывается ровно то, что задаёт
состояние отрисовки.

`GetColor(ObjType, int)` при этом остаётся, но его место — точечные запросы:
панель свойств, подсказка под курсором, отладка. В контракте это надо написать
прямо, иначе рано или поздно его позовут в цикле.

### Ключ стиля — сам набор, а не его имя

Переименование наборов в Gerbera есть, поэтому ключевать стили строкой нельзя:
после переименования цвет потерялся бы, а набор получил бы новый случайный.

Имя как ключ требовало бы `RenameSet(ObjType, oldName, newName)` на виде и
правила «операция переименования обязана его позвать» — забыл вызвать, цвет
молча сбросился. Ещё одно правило того же сорта, что `ClearSelection` перед
заменой, и такое же молчаливое при нарушении.

Правило не нужно: `ObjectsSet.Name` объявлен как `{ get; internal set; }`, то
есть переименование происходит внутри сборки `Model` и правит **тот же
экземпляр**. Значит ключом надо брать сам `ISetInfo` по ссылке — стиль
переживает переименование сам собой, без единой строчки кода и без правила,
которое можно забыть.

`ISetInfo.Number` в этой роли хуже: у него публичный сеттер, и никто не обещает
его стабильности.

Практические детали:

- `ObjectsSet` не переопределяет `Equals` и `GetHashCode`, так что ссылочное
  равенство работает по умолчанию. Словарь всё же стоит создать с явным
  `ReferenceEqualityComparer.Instance` — это фиксирует намерение и защищает от
  того, что когда-нибудь кто-то добавит `Equals` по имени.
- Словарь держит ссылки на наборы, поэтому удалённый набор не освободится сам.
  `Prune` должен выбрасывать стили наборов, которых больше нет в
  `GetSetsInfo(type)`. С ключом по имени это понадобилось бы точно так же.
- Сигнатуры `IObjectsView` принимают `ISetInfo`, а не строку — совпадают с
  `IModelView` и не заставляют вызывающего доставать имя.

`Changed` и `BeginUpdate` — одно событие на весь вид: сцена, панель свойств,
тулбар и строка состояния подписаны на него.

## Команды как операции над множеством

| Команда | Операция | Номера вне аргумента |
|---|---|---|
| `Select` | объединение | не трогает |
| `Deselect` | вычитание | не трогает |
| `ToggleSelection` | симметрическая разность | не трогает |
| `SetSelection` | замена | снимает выделение |
| `ClearSelection` | опустошение | — |

`SetSelection` держим отдельным методом, а не парой `ClearSelection` +
`Select`: одно уведомление `Changed` вместо двух и невозможно забыть первый шаг.

Каждая команда `IObjectsView` возвращает `bool` «состояние изменилось». По нему
`ModelView` решает, поднимать ли `Changed`, и проверяет `IsEmpty`, чтобы
выбросить запись из словаря. Иначе клик по уже выделенному объекту
перерисовывает сцену без причины.

## Сценарии Gerbera

| Действие | Модификатор | Команда |
|---|---|---|
| клик | нет | `SetSelection` — выделен только кликнутый |
| клик | Shift | `ToggleSelection` — невыделенный добавляется, выделенный выбывает |
| контур | нет | `SetSelection` — выделены только попавшие |
| контур | Shift | `Select` — попавшие добавляются к текущим |
| контур | Ctrl | `Deselect` — попавшие вычитаются из текущих |
| скрыть выделенные | — | `HideSelected()` |
| удалить выделенные | — | операция контроллера, см. ниже |

Модификаторы остаются понятием GUI. Вид даёт команду на каждую операцию над
множеством, чтобы вызывающий выбирал одну, а не собирал её из нескольких.

Отбор попаданий обязан фильтровать по `GetVisible`, иначе контур захватит
скрытое.

### Shift на клике и на контуре означает разное

Клик с Shift снимает выделение с уже выделенного объекта (симметрическая
разность), контур с Shift — не снимает ни с кого (объединение). Это не
опечатка в требованиях, а сознательное разделение: одиночный клик — это
переключатель, контур — накопитель. Зафиксировано здесь, потому что при
рефакторинге возникает соблазн свести обе ветки к одной команде «Shift =
добавить», и тогда клик по выделенному объекту перестанет его снимать.

Ctrl задействован только на контуре, Alt не задействован вовсе.

### Режим «любой тип»

Когда на GUI выбран тип «Объект», попасть может объект любого типа, и выделение
становится многотиповым.

«Объект» — понятие Gerbera, а не элемент `ObjType`: в перечислении только
`Точка`, `Кривая`, `Поверхность`, `Объем`, `Узел`, `Элемент1D`, `Элемент2D`,
`Элемент3D`. Благодаря этому граница проходит сама собой — в `IModelView`
«Объект» попасть не может даже по ошибке, и ключ словаря `views` всегда
конкретный тип. Защитная проверка на входе не нужна.

Роль режима — сказать, какие типы рассматривать при отборе. Результатом в любом
режиме служат пары (фактический тип, номер). Разница только в том, сколько
разных типов окажется в результате.

Отсюда же польза `SelectedTypes` и `TryGetSingleSelectedType`: команды,
требующие однородного выделения (создание группы, условия), в этом режиме
обязаны проверить, что тип один.

### PickHandler — роль, а не существующий класс

В BazisCore такого типа нет, и появиться он там не должен: попадание в объект
считается там, где есть камера, матрицы проекции и буферы, то есть в Gerbera.
На диаграмме он обозначает границу — кто именно вызывает команды выделения.

Его работа — превратить событие ввода в вызовы вида:

1. развернуть точку или контур в попадания, разрешив неоднозначность (клик
   рядом с узлом, лежащим на элементе) по своим правилам приоритета;
2. отбросить скрытое через `GetVisible`;
3. перевести модификатор в команду по таблице выше;
4. вызвать её — для одного типа один раз, для нескольких циклом.

Чего он не делает: не хранит выделение — оно живёт в `ModelView`; не знает о
подсветке — это `GetColor`; не решает, что с выделенным будет дальше.

Набор номеров даёт не только он. В `OperationalController` есть
`ISelectionHelper` с выборками по геометрии: `SelectE2DInPlane`,
`SelectNodeInPlane`, `SelectNodeInDirection` — каждая возвращает номера одного
типа. Это второй поставщик, и он тоже должен заканчиваться вызовом команды
`IModelView`, а не собственной раскраской. Команды вида не должны знать, откуда
пришёл набор: от клика, от контура, от выборки по плоскости или из группы.

На диаграмме `ISelectionHelper` не показан — он уводил картинку за лимит
ширины, а к разделению модели и вида отношения не имеет.

## Многотиповые операции — цикл, а не носитель набора

Все изменяющие команды принимают `ObjType` и `IEnumerable<int>`. Если типов
несколько, вызывающий делает цикл внутри `BeginUpdate`.

Отдельный носитель набора здесь был и убран. Сначала завели `ISelectedObjects`
и `SelectedObjects` — словарь `ObjType -> HashSet<int>` с методом `Add`, чтобы
многотиповая замена была одной атомарной операцией. Доводы против оказались
сильнее:

- атомарность уже даёт `BeginUpdate` — одно `Changed` на весь пакет, поэтому
  главный довод за носителя не работает;
- тип нигде не хранится, он транзитный: возникает на событии мыши и живёт до
  конца вызова. Это словарь, у которого чтение целиком покрывается BCL;
- пять перегрузок в `IModelView` плюс интерфейс плюс класс — заметный вес ради
  того, что делает цикл в три строки на стороне вызывающего.

Цена решения — два правила для вызывающего, оба ниже. Если когда-нибудь набору
понадобится нести что-то ещё (порядок выбора, режим), носитель вернётся.

### Правило 1: замена начинается с ClearSelection

`SetSelection(type, ids)` означает «выделено ровно это», включая другие типы.
В цикле по типам каждый вызов стирал бы предыдущий, поэтому многотиповая замена
пишется так:

```csharp
using (view.BeginUpdate())
{
    view.ClearSelection();
    foreach (var type in hitTypes)
        view.Select(type, GetHits(type));
}
```

Забытый `ClearSelection` даёт накопление выделения от контура к контуру — самая
вероятная ошибка в этой схеме, потому что молчаливая.

### Правило 2: перед изменением — материализовать

`GetSelection()`, `GetSelected(ObjType)` и `SelectedTypes` ленивы. Удаление или
любая другая мутация во время обхода рвёт перечисление. Снимок делает
вызывающий, одним `ToList`, и делает его осознанно — там, где собирается менять
модель.

`GetSelection()` отдаёт `IEnumerable<IModelObject>` через `yield return`:
у объекта есть и `ObjType`, и `Number`, так что вызывающему хватает его одного,
а `ModelView` достаёт объект через `ObjectsData.Find` — это словарь, O(1).

## Последовательность вызовов по сценариям

`view` — это `IModelView`.

**Клик без модификатора, тип выбран**

1. хит-тест, для каждого кандидата `view.GetVisible(type, n)`
2. `view.SetSelection(type, new[] { 42 })`
3. внутри `ModelView`, под `BeginUpdate`: `v.ClearSelection()` у всех записей
   `views`, кроме `type`; `GetOrCreateView(type).SetSelection(...)`; выбросить
   записи с `IsEmpty`; одно `Changed` на выходе

**Клик с Shift, тип выбран**

1. хит-тест, `GetVisible`
2. `view.ToggleSelection(type, new[] { 42 })` → `GetOrCreateView(type).ToggleSelection(...)`,
   другие типы не трогаются

**Контур без модификатора, режим «Объект»**

1. отбор попаданий с `GetVisible`, группировка по фактическому типу
2. `using (view.BeginUpdate())`, затем `view.ClearSelection()` и цикл
   `view.Select(type, numbers)` по типам
3. одно `Changed` на выходе из пакета

**Контур с Shift** — то же без `ClearSelection`: цикл `view.Select(type, numbers)`.

**Контур с Ctrl** — цикл `view.Deselect(type, numbers)`. Внутри `ModelView` эта
команда ищет запись **без создания**: вычитание из несуществующего вида ничего
не даёт, а `GetOrCreateView` насорит пустыми записями.

**Скрыть выделенные**

1. `view.HideSelected()`
2. под `BeginUpdate` по каждой записи `views`: `v.SetHidden(v.GetSelected(), true)`,
   затем `v.ClearSelection()`

Снимок не нужен: всё происходит внутри вида, `SetHidden` пишет в `hidden`,
читая `selected` — это разные множества.

**Удалить выделенные**

```csharp
var doomed = view.GetSelection().ToList();      // правило 2
foreach (var obj in doomed)
    objects.Remove(obj.ObjType, obj.Number);
view.Prune();
```

## Синхронизация с моделью

Номера объектов меняет только явная перенумерация: `ObjectsData.Remove` удаляет
запись из набора, но чужих номеров не трогает. Значит источников рассинхрона
два — удаление (лечится `Prune`) и перенумерация (`Reset`).

### Prune

Скрытость и выделение хранятся по номерам, поэтому вид не узнаёт об удалении
сам: номер удалённого остаётся в множестве. Множества растут от каждого цикла
«создал-удалил», а номера переиспользуются, так что новый объект оказывается
«уже выделенным» или «уже скрытым».

`Prune` спрашивает, а не получает список: вид отдаёт свои номера на проверку
предикату `Predicate<int> exists`. Чистить нужно единицы записей, а список
существующих — это проход по всей модели и лишняя коллекция. Сам вид о модели
не знает, предикат замыкает `ModelView`:

```csharp
IObjectsData objects = model.ObjectData;
bool changed = view.Prune(number => objects.Find(type, number) != null);
```

`ObjectsData.Find` — поиск по словарю набора, O(1), так что стоимость `Prune`
определяется числом записей вида, а не размером модели.

`IModelView.Prune()` обязан проходить по **всем** типам, а не только по тем, что
удаляли. `ObjectsData.Remove` каскадный: удаление точки дёргает
`CurveSet.ClearNotExisted()` и `SurfaceSet.ClearNotExisted()`, то есть уносит с
собой кривые и поверхности. Попытка «оптимизировать» чистку до затронутых типов
оставит в виде номера объектов, исчезнувших по цепочке.

Ради этого предиката сначала были заведены интерфейс `IObjectExistence` и
класс-адаптер `ObjectsExistence`. Два типа делали работу одного параметра —
убраны.

Название `Prune` — из садоводства, «подрезать», срезать засохшие ветки. Если
метафора читается плохо, ясная замена — `RemoveMissing` или `DropMissing`.

### Перенумерация: пока сбрасываем вид целиком

`ObjectsRenumber` карту старый → новый не отдаёт. Принятое решение: после
перенумерации `ProjectController` зовёт `IModelView.Reset()` — выделение и
скрытость теряются, но явно, а не подменяются чужими объектами. `Reset()` обходит виды, снимая
выделение и скрытость, и поднимает одно `Changed`; стили наборов он не трогает
(см. раздел про вынос цвета).

Следствие: **`Remap` в интерфейсах нет**. Метод без вызывающего вводить незачем.
Когда `Renumber` научится отдавать карту, `Remap` вернётся, а `Reset` уйдёт.

Второе следствие: `ObjectsRenumber` ушёл с диаграммы. Он попал туда только из-за
стрелки `Remap`; без неё он никак не связан с представлением и остаётся обычной
операцией над моделью.

### ObjectsRenumber: что он делает

Живёт в `OperationalController.MeshObjsUtility`. Делает сплошную перенумерацию
объектов одного типа: обходит набор и присваивает номера подряд с нуля через
`SetNumber`. Реализован только `ObjType.Узел`; для `Точка` и `Поверхность`
бросает исключение, для остальных — `NotImplementedException`. Ветка для
элементов закомментирована, вместо неё тот же алгоритм живёт вторым экземпляром
в `ProjectController.RenumberElements`, который нумерует `E1D`, `E2D` и `E3D`
сквозным счётчиком.

Старый номер теряется в момент `SetNumber` — отсюда и отсутствие карты.
Перенумерация ничего не удаляет, поэтому `Prune` промолчал бы, а номера в виде
остались бы валидными, указывая на другие объекты: пользователь увидел бы, что
подсвечено не то, что он выделял, без единой ошибки в логе.

Лечится дёшево: `Renumber` возвращает `IReadOnlyDictionary<int,int>` — обход
объектов всё равно идёт, достаточно запомнить старый номер перед `SetNumber`.
Заодно стоит свести `RenumberElements` в ту же реализацию.

### Удаление выделенных

Удаление меняет модель, поэтому его нет в `IModelView`: вид хранит состояние, а
не командует моделью. Место операции — `ProjectController`, у которого есть и
модель, и вид. Порядок обязателен:

1. снимок выделения (`ToList`) — до изменений
2. `objects.Remove(type, number)` по каждому объекту снимка
3. `view.Prune()`

Без шага 1 удаление рвёт перебор выделения. Без шага 3 номера удалённых
остаются в множествах.

### Скрытие снимает выделение

Иначе следующая команда — удаление, фаска, создание условия — выполнится над
объектами, которых пользователь не видит. `HideSelected()` делает скрытие и
`ClearSelection()` одним пакетом.

## Что сценариями не востребовано

Не мешает, но и не оправдано, пока не назван сценарий:

- `ClearSelection(ObjType)` — снять выделение одного типа. Ни клик, ни контур
  этого не делают.
- `SetVisible(ObjType, IEnumerable<int>, bool)` — скрытие идёт только от
  выделения, через `HideSelected()`. Форма с номерами нужна разве что команде
  «скрыть всё, кроме выбранного».
- `GetColor(ISetInfo, int)` — сценариями выделения не востребован, но нужен
  сборке буферов по наборам, см. «Что получает презентер».

## Цвет уходит из Model целиком

Часть работы уже сделана в коде: `IModelObject` сегодня содержит только `Dim`,
`Number`, `ExistState`, `ObjType`, `CalcCentr` и `SetNumber` — `Color` и
`ViewState` из него убраны, а `ICoordinated` переехал в
`PrGeometry\Interfaces`.

Остался ровно один очаг: интерфейс `ISetView` в `Model.Interfaces.ObjectsCollections`
с `Color`, `ViewMode`, `SetColor`, `SetViewMode`. Его наследует `ISetInfo`, то
есть цвет и режим отрисовки висят на наборе объектов внутри расчётной
библиотеки. Убрать стоит, и код этому не сопротивляется.

**Цвета наборов нигде не сохраняются.** `SaveModelToBPF2TextFile` про цвет
молчит, а `LoadModelFromBPF2TextFile` при загрузке присваивает каждому набору
**случайный** цвет — `Color.FromArgb(rnd.Next(256), rnd.Next(256), rnd.Next(256))`,
три места подряд. Значит переносом ничего не ломается в форматах файлов: цвет
и сегодня не переживает перезагрузку. Заодно генерация случайных цветов уезжает
из загрузчика модели, где ей делать нечего.

Что появляется взамен:

- Стиль набора (цвет и `ViewMode`) живёт **внутри `ObjectsView`**, в маленьком
  словаре по имени набора. Второго словаря в `ModelView` нет.

  Сначала я завёл в `ModelView` отдельный `setStyles` с ключом «тип плюс имя
  набора» и выписал исключение из собственного правила «новое состояние — поле
  внутри `ObjectsView`». Исключение было лишним: набор принадлежит ровно одному
  `ObjType`, а имя набора внутри типа уникально — об этом прямо говорит
  сигнатура `IObjectsData.GetSetInfo(ObjType, setName)`. Значит ключ
  раскладывается на те же две ступени, что и всё остальное: `ObjType` выбирает
  вид, имя ищется внутри. Правило снова без исключений.

  Две ловушки, которые объединение создаёт, и обе надо держать в голове:

  - **`IsEmpty` обязан учитывать стили.** Вид с раскрашенным набором, но без
    выделения и скрытости, выбрасывать из словаря нельзя — потеряется цвет.
  - **`Reset()` больше не `views.Clear()`.** Перенумерация меняет номера, а не
    состав и цвета наборов, поэтому `Reset` обходит виды и зовёт у каждого
    `ClearSelectionAndHidden()`, оставляя стили. С отдельным словарём это
    получалось само собой, теперь требует внимания.

  Если внутри `ObjectsView` станет тесно, стили можно вынести в отдельный
  объект-помощник, которому вид делегирует, — снаружи ничего не изменится.
- Цвет новому набору назначает `ModelView` при первом обращении — палитрой или
  случайно, как сегодня делает загрузчик.
- `GetColor(ISetInfo, int)` в `IModelView` остаётся и становится основным: по
  нему сборка буферов красит объекты набора. Точечный `GetColor(ObjType, int)`
  делегирует ему, разрешив набор через `GetSetInfo`.
- Появляются `GetSetColor` / `SetSetColor` и `GetViewMode` / `SetViewMode`:
  раскрасить набор пользователь по-прежнему должен уметь, но теперь это команда
  вида, и она поднимает `Changed` — сейчас `ISetInfo.SetColor` меняет цвет мимо
  всяких уведомлений.
- `IObjectsData.SetBackColor(ObjType)` удаляется.
- `ISetView` исчезает как интерфейс, `ISetInfo` становится чисто
  информационным: имя, номер, тип, количество, номера, координаты, центр.

Чего это **не** даёт, чтобы не было завышенных ожиданий: `Model` не перестанет
ссылаться на `System.Drawing`. `System.Drawing.Color` лежит в
`System.Drawing.Primitives`, это часть платформы и работает кроссплатформенно —
проблемы переносимости здесь нет и не было. Довод чисто архитектурный:
единственный владелец цвета вместо двух.

Цена — правки во всех местах, где сегодня зовут `ISetInfo.SetColor` и читают
`ISetInfo.Color`, плюс чистка реализаций `ObjectsSet`, `SurfacesSet` и
`DefaultSetInfoComparer`.

## ICoordinated переезжает в Geometry

`ICoordinated` объявлен в `Geometry` (`PrGeometry\Interfaces\ICoordinated.cs`),
а не в `Model` — этот шаг в коде уже сделан. Структурно он законен: `Model` уже ссылается на `Geometry`, там же
живёт `Point3D`, который интерфейс возвращает, — цикла не возникает. По смыслу
тоже верно: «сколько у объекта точек и какие» — чистая геометрия, к расчётной
модели отношения не имеет.

**Но зависимость PostProc от Model это не снимает.** Ожидание было именно такое,
и оно не подтвердилось. По коду PostProc ссылается на `Model.csproj` и
использует оттуда:

| Тип | Упоминаний | Где |
|---|---|---|
| `IModelObject` | 17 | `ResultFigure`, `ResultSurface`, `ResultPoint` — они его реализуют |
| `ObjType` | 8 | там же |
| `IPoint` | 5 | `ResultsFieldsCreator`, `IsoLevelFieldsCreator` |
| `ISurfaceElement` | 4 | `ResultsFieldsCreator` |
| `ILineObject` | 4 | `LineGradientsCreator` |
| `ISurfaceObject` | 1 | `ResultFigure` реализует его |
| `Node` | 1 | `ResultsFieldsCreator` |

Все восемь затронутых файлов лежат в `ScenePresenter`; остальной PostProc —
экспорт, слияние результатов, контроллер — про `Model` не знает вовсе.

Дальше зависимость распадается на две части.

**Уйдёт само.** `IModelObject` и `ObjType` — это 25 из 40 упоминаний, и почти
все они в `ResultFigure`/`ResultSurface`/`ResultPoint`, которые сегодня
реализуют `Number`, `ObjType`, `ViewState`, `Color`, `SlaveColor`,
`InitialColor`, `Dim`, `CompareTo`, `Equals`, `GetHashCode`, `SetNumber` — при
том что `Number` у них всегда 0, а `ObjType` захардкожен «Поверхность». Это
ровно та уборка, что уже записана ниже: объекты сцены перестают быть объектами
модели.

**Останется по-настоящему.** `ResultsFieldsCreator`, `IsoLevelFieldsCreator` и
`LineGradientsCreator` читают сетку — `Node`, `ISurfaceElement`, `ILineObject`,
`IPoint`. Поля результатов строятся по узлам и элементам, это суть работы, а не
случайная связка. Снять её можно двумя способами: перенести и эти интерфейсы в
`Geometry` (они тоже описывают форму, а не расчёт), либо завести в PostProc
собственный контракт на «источник сетки» и реализовать его на стороне Model.

Итого перенос `ICoordinated` был правильным и дешёвым, но это первый шаг из
трёх, а не решение задачи целиком.

## Заодно к уборке

- `ISurface<T>` переобъявляет `NumberOfPoints` своей копией — наследовать
  `ICoordinated`.
- В `IModelObject` соседствуют `Dim` и `ObjType`, хотя `ObjType` однозначно
  задаёт размерность, а `Dim` хранится полем и может с ним разойтись.
- `ResultFigure`/`ResultSurface`/`ResultPoint` больше не `IModelObject`: это
  объекты сцены (`Number` всегда 0, `ObjType` захардкожен, цвет задаётся шкалой
  `ItemRange`). Отсюда же уходят `CompareTo`, `Equals`, `GetHashCode`,
  `SetNumber`, `SlaveColor`, `InitialColor`, `Dim`.

## NullModelView удалён

Проверено по коду 21.09.2026, до удаления.

**В тестах он не использовался ни разу.** `TestProject\ControllerTests\ModelViewTests.cs`
одиннадцать раз строит настоящий `new ModelView(...)`. Версия «держим ради
тестов» не подтвердилась.

Создавался он в двух местах:

1. `ProjectController.ModelView`, когда `ModelData == null` — «проект не
   открыт»;
2. перегрузки `PresentersCreator` без вида и безпараметрические конструкторы
   презентеров. Этих перегрузок нет в `IPresentersCreator`, то есть код,
   работающий через интерфейс, до них не дотягивался.

### Принятое решение

Отсутствие вида — не катастрофа, а нормальное состояние «модель не загружена».
Поэтому `NullModelView` удалён целиком, а `ProjectController.ModelView`
возвращает `null`, пока модели нет. Перегрузки без вида и безпараметрические
конструкторы презентеров удаляются вместе с ним.

Что этим выигрывается: правила цвета существуют ровно в одной реализации.
До удаления `NullModelView` дублировал `GetDisplayColor`, разбор цвета из
`ModelView` и `GetDefaultViewMode` из `ObjectsView`, причём цвет по умолчанию
уже разошёлся — `ObjectsView` раздавал палитру (`SteelBlue`, `Orange`,
`MediumSeaGreen`, ...), а `NullModelView` возвращал `DarkGray` для всего, кроме
узлов. Одна модель выглядела по-разному в зависимости от того, какой вид
подставлен. Второго источника умолчаний больше нет.

Заодно уходит дефект: геттер создавал `new NullModelView(null)` при каждом
обращении, из-за чего `ReferenceEquals` в `SubscribeToModelView` всегда был
ложен, и Gerbera на каждом вызове переподписывалась на одноразовые объекты с
пустыми `add`/`remove`. С `null` этот путь просто не выполняется.

### Чем платим

Проверка на `null` переезжает к вызывающему. В Gerbera это **71 обращение к
`project.ModelView` в 26 файлах** (по 137 просмотренным файлам из 284). Часть
уже написана безопасно — `ModelViewOperations.SubscribeToModelView` использует
`project?.ModelView` и корректно отрабатывает пустое значение, — но, например,
`ApplySelectionColor`, `IsSelected` и `GetVisibleNumbers` там же обращаются
напрямую и получат `NullReferenceException`, если их позовут до загрузки
модели. Внутри CORE аналогично: `ProjectController.SetSelection` зовёт
`ModelView.SetSelection(...)` без проверки.

Практически большинство этих мест недостижимо без открытой модели: нет модели —
нет наборов, нет объектов на сцене, нет условий и групп в навигаторе. Но
полагаться на это молча не стоит: места, которые могут сработать при пустом
проекте (обработчики меню, применение настроек, очистка сцены), нужно пройти
глазами и закрыть ранним выходом.

### Что остаётся непреложным

Презентеры `null` не принимают: конструктор бросает `ArgumentNullException`.
Это не обход, а контракт — нет вида, нечего и собирать, а в пустой модели нет
и наборов, так что цикл сборки просто не выполнится.

## Что получает презентер

Презентеру нужны видимость объекта и его цвет. Перебрали пять вариантов,
прежде чем нашёлся правильный, и все промежуточные разбились об один и тот же
камень: презентер получал *способ спросить* про вид вместо *ответа*.

**`IObjectsView` вместо `IModelView` полем.** Отклонено: в нём нет
`SelectionColor` и `Transparency` — они общемодельные. И он изменяющий:
`Select`, `SetHidden`, `Prune`.

**`ISetDisplay` как поле презентера.** Заводился и отменён: интерфейс плюс
класс ради кэша из двух значений, да ещё с семантикой снимка, за которой надо
следить.

**Создание презентеров внутри `ModelView`.** Отклонено: вид получил бы
зависимость от слоя отрисовки и вторую ответственность — фабрику графических
объектов. Плюс результаты PostProc собираются презентером, которому вид не
нужен вовсе.

**`IModelView` плюс `ISetInfo` полями, как в коде сегодня.** Работает, но в
презентер уезжает тридцать членов интерфейса вместо двух вопросов, и он
теоретически может позвать `Reset()` посреди сборки.

**`IDrawState` параметром каждого метода сборки.** Снимал вопрос устаревания —
состояние живёт один вызов, — но ломал сам объект: презентер без переданного
состояния ничего не мог, то есть самостоятельным объектом не был, а четыре
сигнатуры обрастали параметром. Попытка накрыть тем же интерфейсом градиентные
фигуры PostProc довела до `ScaleDrawState` в `OperationalController` — типа
пост-процессора в чужой сборке. Это и был признак, что абстракция подгоняет под
себя раскладку проектов, а не наоборот.

### Принято: два списка — объекты и цвета

Презентер получает результат, а не источник:

```csharp
public SurfaceObjsPresenter(IReadOnlyList<ISurfaceObject<T, U>> objects, IReadOnlyList<Color> colors)
{
    if (objects == null) throw new ArgumentNullException(nameof(objects));
    if (colors == null) throw new ArgumentNullException(nameof(colors));
    if (objects.Count != colors.Count)
        throw new ArgumentException("Число цветов не совпадает с числом объектов");

    this.objects = objects;
    this.colors = colors;
}

public SurfaceObjsPresenter(IReadOnlyList<ISurfaceObject<T, U>> objects, Color color)
```

Списки параллельны: `colors[i]` — цвет `objects[i]`. Длины сверяются в
конструкторе, дальше индекс общий и проверять нечего.

`IObjsPresenter` возвращается к сигнатурам без параметра состояния:

```csharp
public interface IObjsPresenter
{
    string Name { get; }
    ViewMode ViewMode { get; set; }
    PresenterType PresenterType { get; }

    Tuple<int,int,int,int> CreateIndexes();
    int[] CreatePointers(int indexLength);
    float[] CreateVertexes(int vertexLength, string vertexType);
    bool[] CreateEdgeFlags(int edgesLength);
    int Count();
}
```

**Только видимые.** Список объектов уже отфильтрован, поэтому проверок
видимости внутри презентера нет вовсе — ни `IsVisible`, ни `GetVisible`. Скрыть
объект значит не положить его в список.

**Вторая перегрузка — один `Color` на всех.** Нормали и предпросмотр не
выделяют массив из N одинаковых значений. Четыре случая закрываются двумя
конструкторами, и ни одного нового типа не появляется.

### Кто собирает цвета

| Случай | Кто собирает | Чем |
|---|---|---|
| набор модели | `ProjectController` | `GetVisible` отсеивает, `GetColor(ISetInfo, int)` красит |
| результаты PostProc | Gerbera | шкала `ItemRange` по значению в объекте |
| нормали, предпросмотр | место вызова | один `Color`, вторая перегрузка |
| объекты вне `ModelData` | место вызова | один `Color` либо собственный массив |

Ответ на вопрос «как рисовать» даётся стандартными типами — `IReadOnlyList<T>`
и `Color`. Поэтому в сигнатурах создателя вида нет, `ScaleDrawState` не нужен,
а из `PresentersCreator` исчезают парные перегрузки «с видом» и «без вида»
вместе с `CoordinatedSurfaceObjsPresenter`.

### Чем это лучше предыдущих попыток

- Презентер — законченный объект: после конструктора он умеет всё, что обещает
  интерфейс. Это и было главное возражение против варианта с параметром.
- Устаревать нечему: цвета посчитаны на момент создания, а презентер набора
  пересоздаётся на `Changed` — как и сегодня.
- Ни одного нового типа: ни `ISetDisplay`, ни `IDrawState`, ни `Colored<T>`.
  `Colored<T>` в BCL нет — `Tuple`/`ValueTuple` пришлось бы либо заворачивать в
  свой тип (снова новый тип, да ещё в спорной сборке), либо тащить кортежи в
  публичные сигнатуры, чего мы избегаем.
- Правило цвета остаётся в одном месте — в `ModelView.GetColor`. Три вершинных
  сборщика, которые сегодня дублируют «выделен → `SelectionColor`», получают
  готовый цвет и правила не знают.

### Чем платим

Два списка на набор — это две аллокации на пересборку. Размер их равен числу
видимых объектов набора, то есть той же величины, что и буфер вершин, который
строится тут же рядом; на фоне VBO это незаметно.

Второе — дисциплина вызывающего: положить в списки одно и то же количество и в
одном порядке. Проверка длины в конструкторе ловит первую половину ошибки,
порядок не ловит никто. Это цена за то, что презентер не знает о виде.

### Следствия для `IModelView`

`GetColor(ISetInfo, int)` остаётся и получает главного вызывающего — сборку
буферов по наборам, см. «Где живёт цикл отбора». `GetColor(ObjType, int)`
остаётся для точечных запросов: панель свойств, подсказка под курсором,
отладка.

`GetDisplayColor(Color)` уходит внутрь `ModelView`: по коду его звали два
цветовых сборщика (теперь они получают готовый цвет), сам `ModelView` и
удалённый `NullModelView`; в Gerbera — ни разу.

### Осталось решить

`ViewMode` сейчас живёт на презентере свойством с сеттером, хотя по смыслу это
стиль набора и он уже есть в `SetStyle`. Перенос потребует тронуть `IVBObject`
и `VBOController` в Gerbera, поэтому отложен и в этот заход не входит.

## Где живёт цикл отбора

Списки кто-то должен наполнить. Рассматривались два места.

**Метод вида.** `IModelView` получил бы пару обобщённых методов:

```csharp
IEnumerable<TObj> GetVisible<TObj>(ISetInfo setInfo, IEnumerable<TObj> objects) where TObj : IModelObject;
IReadOnlyList<Color> GetColors<TObj>(ISetInfo setInfo, IReadOnlyList<TObj> objects) where TObj : IModelObject;
```

Отклонено. Параметр типа здесь понадобился не по делу: внутри вида тип объекта
стирается до `IModelObject`, а презентеру нужен `ISurfaceObject<T, U>`, поэтому
тип пришлось бы протаскивать обратно только затем, чтобы не появилось
приведение вниз. Дженерики решали проблему, которую сами же и создавали.
Плюс два новых члена в интерфейсе, где их и так три десятка.

**Метод контроллера — принято.** У `ProjectController` типизированная коллекция
уже на руках, стирать нечего, обобщения не нужны:

```csharp
public IObjsPresenter CreateSetPresenter(ISetInfo setInfo)
{
    var visible = new List<ISurfaceObject<T, U>>();
    var colors = new List<Color>();

    foreach (var obj in surfaceObjs)
    {
        if (!modelView.GetVisible(obj.ObjType, obj.Number))
            continue;

        var color = modelView.GetColor(setInfo, obj.Number);
        visible.Add(obj);
        colors.Add(color);
    }

    return creator.CreateSurfaceObjectsPresenter(visible, colors);
}
```

Переезжает **цикл**, а не **правило**. Правило «выделен → `SelectionColor`,
иначе цвет набора, затем `Transparency`» остаётся в `ModelView`: контроллер
цвет спрашивает, а не вычисляет. Обход знанием не является, поэтому его вынос
ничего не размазывает.

### Условие: цикл существует ровно в одном методе

Если он окажется в двух местах, вернётся худшая ошибка этой схемы — забытый
`GetVisible` и молча отрисованные скрытые объекты. Раньше от неё защищал сам
презентер, теперь защищать некому: он про видимость не знает вовсе.

Поэтому сборка набора — метод контроллера, а не код на стороне Gerbera:

```csharp
public IEnumerable<IObjsPresenter> CreateModelPresenters(ObjType objType)
{
    var sets = modelData.ObjectData.GetSetsInfo(objType);
    foreach (var setInfo in sets)
    {
        var presenter = CreateSetPresenter(setInfo);
        yield return presenter;
    }
}
```

Диспетчеризация по `ObjType` на точки, линии и поверхности переезжает в
`CreateSetPresenter` вместе с циклом — иначе «одно место» окажется тремя, по
одному на вид геометрии.

Побочный, но важный эффект: `RefreshModelSetBuffer` в Gerbera становится
короче, а не длиннее — он получает готовые презентеры и раздаёт их в VBO. Это
единственный способ удержать оценку «85% Gerbera не трогаем»: если писать цикл
с `GetVisible` и `GetColor` на стороне GUI, изменённых файлов станет заметно
больше.

### Судьба `GetColor(ISetInfo, int)`

Этот член в ходе проработки убирался и возвращался трижды, поэтому решение
стоит зафиксировать вместе с правилом, по которому оно принято: **член живёт в
интерфейсе, только если назван вызывающий вне `ModelView`.**

Здесь вызывающий назван — `CreateSetPresenter`. Член остаётся.

## Внутренние грани объёмных элементов

Раздел написан по следам регрессии: при переходе на `ModelView` (коммит
`18f74ce`, 18.09.2026) пропала возможность не рисовать грани 3D-элементов,
закрытые соседними элементами. Одновременно исчезли `ChangeInsideSurfacesState`
из `IMeshCommands` и `ProjectController`, алгоритм `MeshObjsUtility/ChangeInsideSurface`
и учёт `ViewState` отдельных граней в презентерах.

### Это не украшение, а обязательный шаг

Для сетки из гексаэдров N×N×N всего граней 6N³, на поверхности 6N² — отношение
ровно N. Для 50×50×50 (125 тыс. элементов) это 750 тыс. граней против 15 тыс.

По текущему коду `CreateIndexes` на треугольник отводит 9 float координат и
12 float цвета, то есть 42 float на четырёхугольную грань — 168 байт.

| | граней | координаты и цвет |
|---|---|---|
| все грани | 750 000 | ~126 МБ |
| только внешние | 15 000 | ~2,5 МБ |

Это видеопамять, и она пересобирается на каждый `Changed`. Без отсечения
объёмная сетка рабочего размера неотображаема.

В других пакетах это называется free faces (Femap, HyperMesh), skin (Abaqus),
surface extraction (VTK — `vtkDataSetSurfaceFilter`, через него ParaView строит
представление Surface). Алгоритм везде один: грань с двумя владельцами
внутренняя. То есть удалённый код реализовывал канонический подход.

Важно, что другие уровни отсечения его не заменяют. Z-буфер даёт верную картинку
только в непрозрачном режиме и платит за всю геометрию. Backface culling убирает
половину оставшегося, но внутренние грани не трогает. Occlusion culling решает
другую задачу — деталь за деталью в сборке — и платит за это каждый кадр, тогда
как внутренняя грань скрыта всегда и убирается один раз.

Отсюда же следствие для текущего состояния: в полупрозрачном режиме внутренние
грани сейчас проступают сеткой внутри детали, а совпадающие грани соседних
элементов дают z-fighting при вращении.

### Почему нельзя вернуть старый метод

`ChangeInsideSurfacesState` совмещал три вещи: вычисление совпадающих граней,
хранение результата в `surface.ViewState` и чтение этого поля презентером.
Второе мы убрали намеренно — и правильно: грань не имеет собственного номера,
ключ `(ObjType, Number)` её не адресует, а хранимая производная величина
немедленно потребовала бы синхронизации с `Prune`, `Reset` и перенумерацией.

Первое и третье восстанавливаются по отдельности.

### Принято: грань знает своих хозяев

Признак не хранится вовсе — хранится **связь**, а `IsInner` считается на ходу.

Устройство взято у `Node`, где это уже сделано: узел держит `List<IElement>` с
`AddElement`, `RemoveElement` и `GetElements()`, и его `ExistState` каскадно
гасит владеющие элементы. То есть владение в этой модели — не справка, а
поддерживаемая связь.

Грань отличается тем, что одного владельца знает с рождения: её строит
собственный элемент. Поэтому нового поля нужно ровно одно — сосед.

```csharp
public class ElementSurface : ISurface<Node>
{
    Node[] nodes;
    readonly IElement owner;
    IElement neighbour;

    public ElementSurface(IElement owner, int surfaceNumber, Node[] nodes)
    {
        if (nodes.Length < 3)
            throw new Exception("Для создания поверхности требуется не меньше 3-х узлов!");

        this.owner = owner ?? throw new ArgumentNullException(nameof(owner));
        this.nodes = nodes;
        Number = surfaceNumber;
    }

    public int Number { get; }

    public int ElementNumber => owner.Number;

    public bool IsInner => neighbour != null && neighbour.ExistState;

    public IEnumerable<IElement> GetElements()
    {
        yield return owner;

        if (neighbour != null)
            yield return neighbour;
    }

    public int[] CreateNodesKey()
    {
        var key = new int[nodes.Length];
        for (var index = 0; index < nodes.Length; index++)
            key[index] = nodes[index].Number;

        Array.Sort(key);
        return key;
    }

    internal void SetNeighbour(IElement element)
    {
        neighbour = element;
    }
}
```

Конструктор принимает элемент, а не его номер: номер тогда не дублируется, а
ссылка переживает перенумерацию — `ObjectsRenumber` уже был источником тихих
ошибок, и повторять это на новом поле не стоит.

Список хозяев по образцу `Node` был бы буквальнее, но дороже: 750 тыс. граней —
это 750 тыс. объектов `List` с их массивами, порядка 50 МБ и полтора миллиона
объектов для GC. Снаружи `GetElements()` выглядит как у узла, внутри это две
ссылки без единой аллокации.

**Бонус от `ExistState` в `IsInner`.** Удаление элементов само обнажает грани
соседей — без разлинковки и без единого вызова. А удаление в GUI и есть самая
частая правка сетки. Поэтому `Mark` нужен только после **добавления** элементов,
а не после любой правки. Хранимый `bool` здесь соврал бы и показал полость
сплошной.

### Признак объявляется на `ISurface<T>`

Не на `ElementSurface` и не на `IElementSurface`, хотя по смыслу место там.
Причина в типах: `ISurfaceElement : ISurfaceObject<ElementSurface, Node>`
подставляет конкретный класс, а презентер обобщён как
`SurfaceObjsPresenter<T, U> where T : ISurface<U>`. Член, объявленный ниже
`ISurface<T>`, презентеру не виден без приведения вниз.

У `GeometrySurface` и `SurfaceFigure` ответ всегда отрицательный — три строки.
`ResultSurface` в реализацию не попал: он `ICoordinated`, а не `ISurface<T>`,
и идёт через `SurfaceObjsPresenter<T>` — ту перегрузку, которая про грани
ничего не знает.

### Связывание

```csharp
public class MarkSurfaces
{
    public IReadOnlyList<ElementSurface> Mark(IEnumerable<ISurfaceElement> elements)
    {
        if (elements == null) throw new ArgumentNullException(nameof(elements));

        var found = new Dictionary<int[], ElementSurface>(new SurfaceNodesComparer());
        var defects = new List<ElementSurface>();

        foreach (var element in elements)
        {
            if (!element.ExistState)
                continue;

            foreach (var surface in element.GetSurfaces())
                Link(surface, found, defects);
        }

        return defects;
    }

    private void Link(ElementSurface surface, Dictionary<int[], ElementSurface> found, List<ElementSurface> defects)
    {
        surface.SetNeighbour(null);

        var key = surface.CreateNodesKey();
        var opposite = default(ElementSurface);

        if (!found.TryGetValue(key, out opposite))
        {
            found[key] = surface;
            return;
        }

        if (opposite == null)
        {
            defects.Add(surface);
            return;
        }

        opposite.SetNeighbour(surface.Owner);
        surface.SetNeighbour(opposite.Owner);

        // Пара закрыта. Пустая запись отличает "встретилась дважды"
        // от "встретилась один раз" и ловит третьего владельца.
        found[key] = null;
    }
}
```

Один проход, а не два: со ссылкой соседа можно проставить сразу при встрече
пары, счётчик не нужен.

`SetNeighbour(null)` делается для каждой грани до поиска в словаре — повторный
`Mark` после добавления элементов должен рвать старые связи, иначе грань,
ставшая внешней, останется помеченной внутренней.

Третья одинаковая грань — дефект сетки: пара уже связана, и молча затереть
соседа нельзя. Закрытую пару отмечает пустая запись в словаре, а не `IsInner`
первой грани: `IsInner` ложен, когда сосед погашен, и третий владелец тогда
прошёл бы как обычная пара. Дефектные грани возвращаются вызывающему —
`MarkSurfaces` живёт в `Model` и об отчётах ничего не знает; сообщение
собирает `ProjectController`.

**Ключ строит сама грань, но не запоминает.** `CreateNodesKey` живёт в
`ElementSurface`: ключ — функция её узлов, и знать о них должна она. Внутри
класса есть прямой доступ к `nodes`, поэтому одна аллокация вместо четырёх —
ни `List`, ни `ToArray`, ни итератора `GetVertexes()`.

Сохранять результат мы отказались. `IModelObject.SetNumber` делает номера узлов
изменяемыми, и после перенумерации сохранённый ключ молча неверен — не только по
значениям, но и по порядку сортировки. Это та же ловушка, из-за которой соседом
хранится ссылка, а не номер. Публичный сеттер `this[int ind]` добавляет второй
путь к устареванию. При этом ключ нужен только внутри `Mark`, а массивы живут
и умирают в нулевом поколении — самый дешёвый сценарий; кэш перевёл бы 750 тыс.
массивов во второе поколение навсегда, около 30 МБ. Инвалидация обошлась бы
в полный обход граней, то есть в тот самый проход, ради которого кэш заводился.

**Компаратор нужен свой.** Существующий `ElementSurfaceEqualityComparer`
делегирует в `s.GetHashCode()`, а `ElementSurface` его не переопределяет —
возвращается хеш по ссылке, и в `Dictionary` равные грани получают разные хеши.

```csharp
public class SurfaceNodesComparer : IEqualityComparer<int[]>
{
    public bool Equals(int[] first, int[] second)
    {
        if (first.Length != second.Length)
            return false;

        for (var index = 0; index < first.Length; index++)
        {
            if (first[index] != second[index])
                return false;
        }

        return true;
    }

    public int GetHashCode(int[] nodeNumbers)
    {
        var hash = 17;
        foreach (var number in nodeNumbers)
            hash = hash * 31 + number;

        return hash;
    }
}
```

Ключ переменной длины, поэтому квадратичные элементы (`Tetra_c`, `Triangle_c`)
проходят без оговорок.

### Откуда зовётся

`ProjectController.MarkModelSurfaces()` проходит `E3DCollection.GetObjects()` —
все наборы сразу, потому что грань может быть общей для элементов из разных
наборов, и понаборный проход оставил бы такую грань внешней. Двумерные элементы
в обход не входят: их единственная грань совпала бы с гранью объёмного соседа и
исчезла бы вместе с ней.

Точки вызова — только те, где элементы **появляются**:

| Место | Что происходит |
|---|---|
| `Load` | загрузка проекта |
| `ImportMesh` | импорт сетки в новый проект |
| `Append` | слияние модели из файла |
| `GenerateMesh(3)` | построение объёмной сетки |
| `SynchronizeGeometryMesh` | `RefineMesh`, `RecombineMesh` |
| `MergeNodes` | склейка узлов переставляет ссылки в элементах, и грани разъединённых сеток становятся совпадающими |

Удаления в списке нет намеренно: `IsInner` проверяет `ExistState` соседа.
`MergeElements` тоже нет — он переносит элементы между наборами, топологию не
меняя, а обход и так идёт по всем наборам.

### Что получает презентер

Один `bool`. Не маска, не список, не делегат.

```csharp
public SurfaceObjsPresenter(IReadOnlyList<ISurfaceObject<T, U>> surfaceObjects, IReadOnlyList<Color> colors, bool drawInnerSurfaces)
```

```csharp
private IEnumerable<T> GetDrawnSurfaces(int index)
{
    foreach (var surface in surfaceObjects[index].GetSurfaces())
    {
        if (drawInnerSurfaces || !surface.IsInner)
            yield return surface;
    }
}
```

Через этот метод идут все шесть обходов граней: `CreateIndexes`,
`CreateSeparators`, `CreateEdgeFlags` и три вершинных сборщика. У сборщиков
меняется сигнатура — вместо объекта они принимают отобранные грани:

```csharp
void Create(ref int stride, float[] vertexAtributes, IEnumerable<T> surfaces, Color color);
```

Это улучшение и само по себе: сборщик вершин перестаёт знать про объект и
работает с тем, что рисует.

Флаг приходит из `IModelView.HideInsideSurfaces` через `CreateSetPresenter`.
Контракт «презентер о виде не знает» не нарушается: `bool` — такой же
стандартный тип, как `Color`.

`HideInsideSurfaces` общемодельный, а не пер-сетовый: грань может быть общей для
элементов из разных наборов, и пер-сетовый флаг дал бы для одного куска
геометрии два противоречивых ответа.

### Это не повторение ошибки с ViewState

`ViewState` был решением пользователя — что показать. Владение гранью — топология
сетки, того же рода, что связность или `ExistState`. Модель имеет право знать
собственную топологию; вид решает только, рисовать ли внутренние грани.

Побочная выгода: та же связь нужна `NormalsCalculator`, `FindOpenSurfaceNodes` и
`FindBoundaryEdges` — все они по сути спрашивают про внешнюю оболочку.

### Отклонённые варианты

**Вернуть `ViewState` на грань.** Хранимая производная величина со всеми
проблемами синхронизации, ради которых затевалось разделение.

**Маска граней третьим параллельным списком.** `IReadOnlyList<bool[]>` рядом с
цветами. Работало бы, но маски пришлось бы пересобирать при каждой пересборке
буфера, а признак на самой грани не требует ничего.

**Расплющить список до граней.** Единицей презентера стала бы грань. Чинит
отрисовку и ломает выбор: `CreateSeparators()` и `Count()` дают одну запись на
объект, и по ним Gerbera отображает диапазоны VBO обратно на элементы модели.

**Декоратор элемента**, чей `GetSurfaces()` отдаёт только внешние грани.
Презентер не меняется вовсе, но `IModelObject` тянет `IEquatable`, `IComparable`
и `IEqualityComparer`, а `GetEnumerator()` презентера отдаёт объекты наружу:
обёртка уехала бы в Gerbera и перестала быть равной исходному элементу. Ошибка
тихая и всплыла бы в выборе, а не в картинке.

**Отдельный объект-результат с кэшем в `ProjectController`.** Нужен был, пока
признак не жил на грани. С хозяевами на грани кэшировать нечего.

### Дефекты, найденные попутно

- `IElementSurface` лежал неиспользуемым: `ElementSurface` его не реализовывала,
  а весь остальной код работает через `ISurface<Node>`. Интерфейс удалён,
  `ElementNumber` остался обычным членом класса. Заодно удалён `INode` —
  единственная ссылка на него была в `MeshObjsCreator\Delone2D\**`, а эта папка
  исключена из компиляции.
- `ElementSurfaceEqualityComparer` непригоден как компаратор словаря, см. выше.
- `ElementSurface.Equals(ElementSurface)` не переопределяет `object.Equals`,
  поэтому `Contains`/`Distinct` по `ISurface<Node>` его не позовут. Сравнивает
  координаты с допуском и только по трём узлам.
- `SurfacesCreator.CreateSurfacesFromSetOfNodes` статический, перебирает тройки
  узлов за O(n³) и вызывается из закомментированной строки в `Element3D` —
  конкретные элементы строят грани сами. Похоже на мёртвый код.

### Тесты

Регрессия прошла молча, потому что теста не было. Минимум:

- два гексаэдра с общей гранью: 12 граней, 10 внешних, у каждого элемента ровно
  одна грань с `IsInner`;
- одиночный гексаэдр: 6 внешних, ни одной внутренней;
- те же два гексаэдра, затем `ExistState = false` у одного: у второго все грани
  снова внешние, без повторного `Mark`;
- повторный `Mark` после добавления третьего элемента не оставляет старых
  связей.

Написаны: `TestProject/ModelTests/MarkSurfacesTests.cs` (связывание) и
`TestProject/ControllerTests/InnerSurfacesPresenterTests.cs` (отбор граней в
буферах). Второй проверяет то, чего не поймает первый: размеры всех буферов
должны сходиться с `CreateIndexes`, а сепараторы — считать те же грани, иначе
сборщик вершин выйдет за границы массива или диапазоны VBO разъедутся с
элементами. Признак на `ModelView` — в `ModelViewTests`.

### Не проверено

- Передача `this` из конструктора `Hexa` в `ElementSurface` даёт ссылку на ещё
  не достроенный объект. Сейчас безопасно — грань обращается к `owner` только
  после конструктора, — но это ограничение стоит помнить.
- Есть ли в Gerbera режим сечения. Если да, при отсечении плоскостью внутренние
  грани обязаны проступить, иначе деталь выглядит полой; тот же вопрос к
  разнесённому виду.

## Открытый вопрос

В режиме «Объект» при клике по точке, где узел лежит на элементе, приоритет типа
выбирает обработчик по своим правилам или пользователь через настройку? От
ответа зависит, нужен ли виду фильтр допустимых для выборки типов, или это
целиком забота Gerbera.
