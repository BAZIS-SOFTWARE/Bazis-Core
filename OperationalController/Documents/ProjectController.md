# ProjectController и ResultController: долгоживущие контроллеры

Документ — пояснительная записка к диаграммам `ProjectController.mdpuml` (изображение —
`ProjectController.png`) и
`ResultDataBase/Documents/ResultController.mdpuml` (картинка —
`ResultController.png`). Предложение, код не изменён. Разобрано по состоянию
на 29.09.2026 (`OperationalController` 4.10.6, `ResultDB` 1.5.3).

Главное требование: **экземпляры `ProjectController` и `ResultController` создаются один раз
на процесс и не пересоздаются** при загрузке проекта, сетки, геометрии или базы результатов.
Заменяются только данные внутри. Отдельный `ProjectSession` в оболочке после этого не нужен.

## 1. Что сейчас

| Что | Где | Следствие |
| --- | --- | --- |
| Оболочка создаёт новый контроллер при открытии проекта и импорте сетки, но переиспользует при импорте CAD | `IODataController.OpenProject`, `ImportMesh`, `BaseForm.OpenProject`; в Avalonia — `MainWindow.LoadProject` | ссылки на контроллер устаревают; у нового контроллера нет инициализированной геометрии |
| Gmsh глобален для процесса | `GmshController.Load`: статическое `GmshKernel.DLL = LoadLibrary(...)` | несколько контроллеров делят одно состояние Gmsh; нужен ровно один |
| Данные внутри контроллера уже заменяются | `Load`, `ImportMesh`, `ImportCAD`, `CreateProject` присваивают поле `project` | основа для «один экземпляр» уже есть |
| `ImportMesh` и `ImportCAD` присваивают новый пустой `ProjectData` **до** загрузки | `Methods/ImportMesh.cs`, `Methods/ImportCAD.cs` | при ошибке загрузки старый проект потерян; из другого потока виден полупустой проект |
| `ModelView` пересоздаётся в геттере при смене `ModelData` | `ProjectController.ModelView` | подписка на `ModelView.Changed` молча теряется; сохранённая клиентом ссылка указывает на представление прежней модели |
| `UnsubMessasge()` обнуляет `MessageEvent` целиком | `IO.cs`; зовётся из `IODataController` после загрузки | с долгоживущим контроллером отпишет и журнал оболочки |
| `FindCoincidentObjects` подписывает лямбду на `ProgressEvent` при каждом вызове | `ProjectController.cs` | на N-м вызове каждое сообщение приходит N раз |
| Выбор загрузчика сетки по расширению продублирован | `ImportMesh`, `Append` | расширение, добавленное в одно место, забудут во втором |
| Событий об изменении данных нет | — | оболочка сама вызывает `PresentGroupDataOnTree()` и т. п. после каждой операции |
| Состояние результатов — поля формы | `BaseForm.ResultDbPath`, `resultTimes`; `new LoadResultsFileDB()` на каждое чтение | у результатов нет владельца в ядре |

## 2. Принципы

1. **Один экземпляр на процесс.** Контроллеры создаёт корень композиции (App / BaseForm) и раздаёт
   ссылку. Ссылка не устаревает никогда, поэтому её можно держать в любом компоненте.
2. **`project` никогда не `null`.** Пустой `ProjectData` создаётся в конструкторе, `HasProject = false`.
   Проверки `project?.` и «Проект не создан» заменяются одним свойством.
3. **Двухфазная замена данных.** `Read*` читает файл и готовит данные, не трогая состояние
   контроллера, — его можно звать в фоне. `Open*` / `Append` / `Close` фиксируют результат одним
   присваиванием в потоке владельца. Исключение — геометрия (раздел 3.3).
4. **События описывают изменение.** `Message` передаёт один вариант `ChangeMessage` с видом
   изменения и адресом затронутой сущности. Актуальные данные подписчик читает из контроллера.
   Для геометрии событие содержит снимок количеств объектов.
5. **Прогресс чтения — процент данных файла.** Клиент передаёт необязательный `IProgress<int>`
   в `ReadProject` или `ReadModel`. Для текстового файла процент равен
   `100 × число прочитанных строк / общее число строк`; для бинарного —
   `100 × число прочитанных байт / общее число байт`. Загрузчик сообщает целое значение от 0 до 100.
   Текстовых сообщений в прогрессе нет. Прогресс не входит в `Message`, которое сообщает только
   об изменениях данных. Оболочка сама показывает статус занятости до завершения всей команды.
6. **Новый `ModelView` для новой модели.** При замене проекта контроллер создаёт представление
   новой `ModelData` и переносит в него только общие настройки вида. Сам `ModelView` и ссылка на
   него не входят в публичный контракт; клиенты работают с представлением через команды и запросы
   `IProjectController`.

## 3. ProjectController

### 3.0. Два уровня

Диаграмма разделена на два уровня внутри сборки `OperationalController`.

- **Уровень 1 — контракт сборки.** `IProjectController` и его составные интерфейсы, включая
  единый `IProjectSession` для состояния и жизненного цикла проекта, `IProjectView`,
  `IObjsPresenter`, аргументы событий,
  `PreparedProject` / `PreparedModel`. Клиенты ядра (BazisGUI, BazisAvaloniaGUI, скрипты IronPython)
  зависят только от этого уровня. Конкретный `ProjectController` создаёт один раз корень композиции
  клиента; дальше в клиенте везде `IProjectController`. Сейчас клиенты держат конкретный тип
  (`ProjectController project` в BaseForm, `SceneView`).
- **Уровень 2 — реализация контракта.** `ProjectController` и то, из чего он составлен: `ModelView`,
  `ModelLoaderFactory`, `MarkSurfaces`, `GmshController`,
  `PresentersCreator` и наборы `MeshObjsUtility`, `MeshObjsCreator`, `GeomObjsCreator`. Снаружи эти
  классы не видны и заменяются без изменения контракта. `ModelView` — внутренний класс реализации:
  публичного свойства `IProjectController.ModelView` и публичного `IModelView` нет.

Ниже уровней — данные (`IProjectData`: `ModelData`, `TaskData`, `GeneralData`) и `GmshApi`.
`PreProc` вызывается клиентом напрямую для формирования расчётных инструкций.
`ResultController` стоит особняком: он не зависит от `OperationalController`, а тот — от него;
клиент держит оба контроллера (раздел 4).

### 3.1. Состояние и жизненный цикл — `IProjectSession`

`IProjectSession` объединяет сведения о текущем проекте (`HasProject`, `FilePath`, `IsModified`,
`Name`, параметры задачи и баз данных) с операциями его создания, чтения, открытия, сохранения
и закрытия. Отдельных `IProjectLifecycle` и `IProjectSessionQueries` в новом контракте нет.

| Было | Стало | `Message.Change` |
| --- | --- | --- |
| `Load(path)` | `ReadProject(path, progress)` → `Open(prepared)` | `ProjectChange(Loaded)` |
| `ImportMesh(path)` | `ReadModel(path, progress)` → `OpenMesh(prepared)` | `ProjectChange(Loaded)` |
| `Append(path)` | `ReadModel(path, progress)` → `Append(prepared)` | последовательные `MeshChange` для затронутых наборов и групп |
| `ImportCAD(path)` | `ImportGeometry(path)` | `ProjectChange(Loaded)` |
| `CreateProject(path)` | `Create(path)` | `ProjectChange(Created)` |
| — | `Close()` | `ProjectChange(Closed)` |
| `Save(path)` | `Save(path)`; при смене пути | `ProjectChange(PropertyChanged, FilePath)` |

Свойства `HasProject`, `FilePath`, `IsModified` доступны для чтения. `IsModified` отмечает
несохранённые изменения и сбрасывается после открытия, создания или сохранения. Отдельных
`StateChanged` и `IsBusy` в контракте нет. Как сообщать об изменении одного только `IsModified`,
диаграмма пока не определяет; доступность команд клиент определяет по текущему состоянию.

`PreparedProject` и `PreparedModel` — непрозрачные результаты чтения: у обоих снаружи виден
путь, у `PreparedProject` также имя; сами данные доступны контроллеру (`internal`).

`progress` необязателен. `ReadProject` сообщает процент при чтении `.bpf` и `.bpf2`.
`ReadModel` передаёт процент от загрузчиков текстовых сеточных форматов (`.inp`, `.inp_v2`,
`.asc`, `.dat`, `.cdb` и текстовый STL) по числу строк, а от загрузчика бинарного STL — по числу
байт. Если загрузчик ещё не поддерживает подсчёт, он не вызывает `Report`; GUI показывает
неопределённый индикатор занятости. Значение не убывает и достигает 100 после всех проходов
чтения файла; для `.bpf` и `.bpf2` учитываются проходы чтения модели и данных задачи, без сброса
процента между ними. Разбор оставшихся данных и последующие `Open`, `OpenMesh` или `Append` могут
продолжаться после 100, поэтому индикатор занятости GUI остаётся до завершения команды.
В текущем коде загрузчики посылают лишь текстовые `LoadEvent`; числовой прогресс ещё требуется реализовать.

### 3.2. Единственная точка замены

`ReadProject` возвращает подготовленные данные без изменения текущего проекта. `Open` передаёт
их в `Replace(data, ProjectChangeKind.Loaded)`: контроллер готовит `ModelView` для новой модели,
заменяет проект и текущее представление, затем публикует `Message(ProjectChange.Loaded)`. Аналогично `Create`,
`OpenMesh`, `ImportGeometry` и `Close` передают в `Replace` соответствующий вид изменения.
`Publish(change)` создаёт `ProjectMessageEventArgs` для всех вариантов изменений.

`MarkModelSurfaces` получает модель параметром: сейчас он работает по `ModelData` текущего проекта
и в фазе чтения отметил бы не те данные. Текстовые `LoadEvent` загрузчика не транслируются в
контроллер; счётчик прочитанных строк передаётся отдельно от них.

`ReadModel` берёт загрузчик из `ModelLoaderFactory.Create(extension)` — один `if`-список расширений
вместо двух.

### 3.3. Геометрия — исключение из двух фаз

Импорт CAD меняет глобальное состояние Gmsh (`Gmsh.Clear()`, `Open`), подготовить его в стороне
нельзя. Поэтому `ImportGeometry`:

1. выполняется без параллельного чтения или изменения данных контроллера: это обеспечивает клиент;
2. собирает новый `ProjectData` в локальной переменной и только в конце вызывает `Replace`;
3. при ошибке вызывает `Replace` с пустым проектом (`Closed`) и пробрасывает исключение: прежнюю
   геометрию в Gmsh уже не вернуть, а оставить старый `ProjectData` поверх очищенного Gmsh — значит
   показать пользователю несуществующую геометрию.

То же правило клиент соблюдает для остальных команд, которые меняют данные контроллера
(`GenerateMesh`, `RefineMesh`, `ExtrudeElement*` и т. п.). `Read*` без побочных эффектов можно
выполнять в фоне; `Open`, `Append` и `Close` фиксируют результат в потоке владельца. Контроллер
сам не обеспечивает потокобезопасность: `BusyScope`, `BeginBusy` и `IsBusy` отсутствуют.

`InitializeGeometry` вызывается один раз при старте приложения.

### 3.4. Изменения данных — `IProjectEvents.Message`

`ProjectMessageEventArgs.Change` содержит ровно один из пяти вариантов `ChangeMessage`:

| Вариант | Данные и назначение |
| --- | --- |
| `GeoChange` | Снимок `Counts`: число точек, кривых, поверхностей и объёмов в CAD после синхронизации с внутренними данными. Все четыре вида присутствуют, включая нулевые значения. Событие публикуется после изменения геометрии, даже если количества остались прежними. |
| `MeshChange` | `DataKind = Set / Group`, `Action = Created / Updated / Deleted`, `ObjectType`, `EntityId`. Последнее поле — устойчивый `Number` набора или группы. Ключ внутри проекта: `DataKind + ObjectType + EntityId`. Изменение состава набора после удаления узла относится сюда. |
| `CondChange` | Вид условия (`DataKind`: нагрузка, закрепление, нагрев, среда, материал), `Action` и `Id` — индекс в списке условий. При удалении это индекс непосредственно до удаления, при создании и изменении — текущий индекс. При отложенной обработке GUI перечитывает список целиком: индексы могли сдвинуться. |
| `ViewChange` | `ChangeKind`, `AffectedSets` и `GetChangeKind(setInfo)` для отдельных наборов. Контроллер преобразует `ModelView.Changed` в `Message(ViewChange)`. |
| `ProjectChange` | `ChangeKind = Loaded / Created / Closed / PropertyChanged`. Только при `PropertyChanged` заполнено `Property`: `Name`, `FilePath`, `TaskKind`, `TaskType`, `MaterialsDB` или `FunctionsDB`. |

При загрузке, создании и закрытии проекта GUI полностью обновляет представление по одному
`ProjectChange`; отдельные события для каждого объекта не нужны. Команды изменения геометрии,
наборов, групп, условий и свойств проекта публикуют соответствующий `Message` после каждого
согласованного шага. Если операция меняет несколько сущностей, сообщения приходят
последовательно по мере её выполнения. Накопителя и `BeginUpdate` у событий проекта нет.
Если смена `TaskKind` или `TaskType` очищает условия, после соответствующего изменения
публикуются отдельные `CondChange`.

Запросы и экспорт (`ExportMesh`, `ExportGeometry`, `SaveSMF`, `CopyFile`) данные проекта не меняют.
Выборки `SelectNodeInDirection`, `SelectNodeInPlane`, `SelectE2DInPlane`, если меняют выделение
через `ModelView`, приводят к `ViewChange`. Изменения настроек генерации сетки
(`SetMesh*Size`, `SetMeshAlgorithm*`, `LoadSMF` и подобные) текущими пятью вариантами явно не
описаны: перед реализацией их уведомления нужно отдельно определить контракт.

### 3.5. Замена внутреннего ModelView

- `ModelView` не публикуется ни как конкретный тип, ни как `IModelView`. Публичные запросы и
  команды представления находятся на `IProjectController` в едином `IProjectView`:
  настройки вида читаются через запросы и меняются командами
  `SetSelectionColor`, `SetTransparency`, `SetHideInsideSurfaces`; там же доступны цвета объектов,
  видимость, выделение и пакет изменений (`BeginViewUpdate`). Контроллер делегирует их текущему
  `ModelView`; интерфейсы не возвращают ссылку на него или его `Model`.
- `Replace` считывает из прежнего представления `SelectionColor`, `Transparency` и
  `HideInsideSurfaces`, создаёт `ModelView` для новой `ModelData` и переносит эти три настройки.
  Если прежнего представления нет, используются настройки по умолчанию. Выделение, скрытость,
  индивидуальные цвета, стили наборов и накопитель `changedSets` в новый экземпляр не переходят.
- Контроллер снимает свою подписку на `Changed` со старого экземпляра и подписывается на новый.
  Новый экземпляр не создаётся в геттере. Перенос настроек не публикует `ViewChange`: после
  замены данных публикуется один `Message(ProjectChange)`, по которому клиент перестраивает GUI.
- Замена проекта не выполняется внутри открытого `BeginViewUpdate`; пакет нужно завершить до
  вызова `Open`, `OpenMesh`, `Create`, `ImportGeometry` или `Close`.
- `Append` не заменяет модель и её представление: выделение и скрытость сохраняются.

### 3.6. Сообщения

- `MessageEvent : Action<string>` и `UnsubMessasge()` удаляются. Вместо них
  `Message : EventHandler<ProjectMessageEventArgs>` передаёт `ChangeMessage` напрямую
  потребителям. Каждый подписчик сам управляет своей подпиской (`+=` / `-=`).
- `Message` не передаёт процент чтения или строки статуса; у `ProjectMessageEventArgs` нет `Text`
  и `Level`. Процент идёт только в `IProgress<int>` конкретного вызова чтения. Оболочка включает
  и выключает собственный индикатор занятости вокруг всей команды.
- `FindCoincidentObjects` не подписывается на текстовый `ProgressEvent`: сейчас такая подписка
  добавляется при каждом вызове. Осмысленная ошибка операции передаётся исключением, а не строкой статуса.
- Диагностика `MarkModelSurfaces`, важная для результата операции, оформляется как ошибка или
  структурированные данные результата; её нельзя маскировать строкой статуса или `ChangeMessage`.

### 3.7. Препроцессор

Формирование расчётных инструкций принадлежит `PreProc`, а не `ProjectController`.
В BazisGUI обработчик меню «Расчёты / Сформировать» получает `TaskKind` и условия
из контроллера, создаёт `ProcessProperty`, затем вызывает `IPreProc.CalcCompDataV2`
и `IPreProc.SortCompDataByTimeAndType`. Интерфейс `IComputationCommands` и зависимость
`OperationalController → PreProc` не нужны.

## 4. ResultController

### 4.1. Где

Диаграмма — `ResultDataBase/Documents/ResultController.mdpuml`. Сборка `ResultDB` (`netstandard2.0`): там уже лежат `Result`, `IResultsLoader` и `LoadResultsFileDB`,
и она не зависит ни от `Model`, ни от `OperationalController`. Контроллер получает `IResultsLoader`
в конструкторе.

### 4.2. Что делает

| Метод | Поведение |
| --- | --- |
| `Read(path)` | схемы таблиц, имена результатов (описатели таблицы `nodes` — как в `FillingResultsData`), имена таблиц, список времён; состояние не трогает, можно в фоне |
| `Open(prepared)` | одно присваивание, `ResultsReplaced(Opened)` |
| `Close()` | пустое состояние, `ResultsReplaced(Closed)` |
| `ReadResult(time)` | чтение кадра по всем таблицам открытой базы; состояние не трогает, можно в фоне |
| `SetCurrent(result)` | `Current`, `CurrentTime`, `CurrentChanged` |
| `GetTimes()`, `GetResultNames()`, `GetTableNames()`, `ContainsTime(time)` | ленивые перечисления через `yield return`; `Kind` — префикс имени файла (термическая / механическая) |

Интерфейс разделён по образцу `IProjectController`: `IResultQueries`, `IResultCommands`,
`IResultFrames`, `IResultEvents`; `IResultController` объединяет их.

`Current` без открытой базы — пустой `Result`, не `null`. Текстовый `LoadEvent` загрузчика
контроллер не транслирует: занятость при чтении базы показывает оболочка.

Кадр, прочитанный до последнего `Open`, не должен стать текущим: `ReadResult` помечает `Result`
внутренней версией открытия, `SetCurrent` отбрасывает кадр чужой версии. Иначе быстрый плеер
после смены базы показал бы кадр из старой.

### 4.3. Чего в нём нет

- **Шкала и построение полей** (`PostProcController.FillRange`, `GetValueColor`, `GetItems`,
  `ResultsFieldsCreator`) — это отображение, остаётся в `PostProc` и оболочке.
- **Пересчёт на узлы** (`MergeResults`) — нуждается в данных модели (`FindInterfacedNodes`),
  поэтому остаётся в `PostProc` и вызывается оболочкой над кадром между `ReadResult` и
  `SetCurrent`, а не над `Current` на месте.
- **Объединение файлов баз** («Результаты / Объединить») — утилита `LoadResultsFileDB.Merge`
  над файлами, после неё — обычный `Read` + `Open`.

### 4.4. Связь с проектом

`ResultController` не ссылается на `ProjectController`, как и сейчас: можно открыть любой `*.db`,
в том числе аргументом `-res`. Закрывать ли результаты при `ProjectChange.Loaded`, `Created`
или `Closed` — решение оболочки (открытый вопрос, раздел 7).

## 5. Как этим пользуется оболочка

```csharp
// открыть проект
// оболочка показывает «Открытие проекта» до завершения всей команды
var progress = new Progress<int>(percent => progressBar.Value = percent);
var prepared = await Task.Run(() => project.ReadProject(path, progress));
project.Open(prepared);                     // UI-поток

// импорт CAD: клиент исключает параллельное чтение и изменение контроллера
project.ImportGeometry(path);

// шаг плеера результатов
var frame = await Task.Run(() => results.ReadResult(time));
results.SetCurrent(frame);
```

- Корень композиции создаёт `ProjectController` и `ResultController` один раз, вызывает
  `InitializeGeometry` один раз и раздаёт ссылки.
- Компоненты Gerbera (навигатор, панель свойств, меню, консоль) получают `IProjectController`
  из корня композиции и подписываются на его `Message` при создании. При освобождении компонента
  подписка снимается. Данные после события читаются через тот же интерфейс; операции
  представления вызываются на контроллере, без доступа к `ModelView`.
- Оболочка показывает статус и занятость из контекста запущенной команды и снимает индикатор
  после её завершения, в том числе при исключении. Если загрузчик поддерживает процент чтения,
  оболочка показывает и его; в остальных случаях использует неопределённый индикатор.
  Контроллеры не отправляют текстовый журнал; `ProjectController.Message` передаёт только изменения данных.
- Контроллеры поднимают события в потоке, где выполнялась операция. Перенос в UI-поток — адаптер
  оболочки (`IUiDispatcher`), не ядро.
- На диаграммах BazisAvaloniaGUI `ProjectSession` заменяется этими двумя контроллерами и адаптером
  событий; `ResultsSession` — `ResultController`.

## 6. Порядок работ

Каждый шаг — отдельная версия пакета.

1. `Message` без текстового статуса и `IProgress<int>` для поддерживаемых загрузчиков;
   удалить `MessageEvent`, `UnsubMessasge`; убрать накопление подписок в
   `FindCoincidentObjects`; `ModelLoaderFactory`.
2. Пустой проект вместо `null`, `Replace` с новым внутренним `ModelView` и переносом общих
   настроек вида; в `ImportMesh` и `ImportCAD` присваивание в конце, а не в начале.
3. `ReadProject` / `ReadModel` / `Open*` / `Append(prepared)`; клиент обеспечивает отсутствие
   параллельного чтения и изменения контроллера.
4. `IProjectEvents.Message` с пятью вариантами `ChangeMessage`; публикация после каждого
   согласованного шага команд, тесты на виды событий и адреса сущностей.
5. `ResultController` в `ResultDB`.
6. Оболочка: один экземпляр контроллеров в BazisGUI (`IODataController.OpenProject` и `ImportMesh`
   перестают создавать контроллер) и в BazisAvaloniaGUI; вызовы `project.ModelView` переводятся
   на команды и запросы `IProjectController`; диаграммы без `ProjectSession`.

## 7. Риски и открытые вопросы

- **Пропущенное событие.** Команд около семидесяти (64 в `I*Commands` плюс команды задачи и `LoadSMF`);
  пропуск оставит GUI с устаревшими данными. Нужны тесты по группам команд на вид `ChangeMessage`,
  действие и адрес сущности, включая каскадные изменения.
- **Потоки.** Контроллер не потокобезопасен. Клиент исключает параллельное чтение и изменение;
  события возникают в потоке выполняемой операции, поэтому GUI переносит обработку в UI-поток.
- **Ошибка импорта геометрии закрывает проект.** Альтернативы при глобальном Gmsh нет.
- **Результаты при смене проекта** — закрывать автоматически или оставлять независимыми, как сейчас?
- **Неописанные уведомления.** Нужно определить события для настроек генерации сетки и решить,
  требуется ли отдельное уведомление при смене одного только `IsModified`.
