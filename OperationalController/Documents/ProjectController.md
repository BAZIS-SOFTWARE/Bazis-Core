# ProjectController: контракт CORE и интеграция с оболочкой

Документ описывает реализованный контракт `ProjectController` в CORE и его диаграммы
`ProjectController.mdpuml` / `ProjectController.png`, `ProjectEvents.mdpuml` / `ProjectEvents.png`.

Оболочка должна создавать один `ProjectController` и сохранять ссылку на него при открытии
проекта, сетки и геометрии. Контроллер заменяет данные внутри себя. Интеграция этого правила
в BazisGUI и BazisAvaloniaGUI остаётся отдельной задачей.

## 1. Принципы

1. **Один экземпляр на процесс.** Контроллер создаёт корень композиции (App / BaseForm) и раздаёт
   ссылку. Ссылка не устаревает никогда, поэтому её можно держать в любом компоненте.
2. **`project` никогда не `null`.** Пустой `ProjectData` создаётся в конструкторе, `HasProject = false`.
   Клиент проверяет наличие проекта через `HasProject`.
3. **Одна команда открытия.** `Open(path)` выбирает по расширению загрузку проекта (`.bpf`,
   `.bpf2`) или сеточной модели (остальные поддерживаемые форматы). `Append(path)` добавляет
   сеточную модель в текущий проект. Открытие заменяет данные только после успешного чтения.
   Импорт CAD учитывает глобальное состояние Gmsh (раздел 2.4).
4. **События описывают изменение.** `Message` передаёт один вариант `ChangeMessage` с видом
   изменения и адресом затронутой сущности. Актуальные данные подписчик читает из контроллера.
   Для геометрии событие содержит снимок количеств объектов.
5. **Прогресс чтения — процент данных файла.** Клиент передаёт необязательный `IProgress<int>`
   в `Open` или `Append`. Для текстового файла процент равен
   `100 × число прочитанных строк / общее число строк`; для бинарного —
   `100 × число прочитанных байт / общее число байт`. Загрузчик сообщает целое значение от 0 до 100.
   Текстовых сообщений в прогрессе нет. Прогресс не входит в `Message`, которое сообщает только
   об изменениях данных. Оболочка сама показывает статус занятости до завершения всей команды.
6. **Новый `ModelView` для новой модели.** При замене проекта контроллер создаёт представление
   новой `ModelData` и переносит в него только общие настройки вида. Сам `ModelView` и ссылка на
   него не входят в публичный контракт; клиенты работают с представлением через команды и запросы
   `IProjectController`.

## 2. ProjectController

### 2.1. Контракт и реализация

Диаграмма разделена на два уровня внутри сборки `OperationalController`.

- **Уровень 1 — контракт сборки.** `IProjectController` и его составные интерфейсы, включая
  единый `IProjectSession` для состояния и жизненного цикла проекта, `IProjectView`,
  `IObjsPresenter` и аргументы событий. Клиенты ядра (BazisGUI, BazisAvaloniaGUI, скрипты IronPython)
  зависят только от этого уровня. Конкретный `ProjectController` создаёт один раз корень композиции
  клиента; после интеграции компоненты оболочки получают `IProjectController`.
- **Уровень 2 — реализация контракта.** Публичный `ProjectController` использует `ModelView`,
  `ModelLoaderFactory`, `MarkSurfaces`, `GmshController`, `PresentersCreator` и операции над
  геометрией и сеткой. Клиенты работают через `IProjectController`, даже если отдельные типы
  реализации в сборке публичны. `ModelView` — внутренний класс: публичного свойства
  `IProjectController.ModelView` и публичного `IModelView` нет.

Ниже уровней — данные (`IProjectData`: `ModelData`, `TaskData`, `GeneralData`) и `GmshApi`.
`PreProc` вызывается клиентом напрямую для формирования расчётных инструкций.

### 2.2. Состояние и жизненный цикл — `IProjectSession`

`IProjectSession` объединяет сведения о текущем проекте (`HasProject`, `FilePath`, `IsModified`,
`Name`, параметры задачи и баз данных) с операциями открытия, создания, сохранения и закрытия.
Свойство `Name` доступно только для чтения. Имя изменяется методом `ChangeProjectName(name)`;
при фактическом изменении метод публикует `ProjectChange(PropertyChanged, Name)` и отмечает
проект изменённым. Повторная передача текущего имени не создаёт события.

| Операция | Метод | `Message.Change` |
| --- | --- | --- |
| Открыть проект `.bpf` / `.bpf2` | `Open(path, progress)` | `ProjectChange(Loaded)` |
| Открыть сеточную модель как новый проект | `Open(path, progress)` | `ProjectChange(Loaded)` |
| Добавить сеточную модель в текущий проект | `Append(path, progress) : void` | `MeshChange` для затронутых наборов и групп |
| Импортировать CAD | `ImportGeometry(path)` | `ProjectChange(Loaded)` |
| Создать пустой проект | `Create(path)` | `ProjectChange(Created)` |
| Закрыть проект | `Close()` | `ProjectChange(Closed)` |
| Сохранить проект | `Save(path)` | `ProjectChange(PropertyChanged, FilePath)` при смене пути |

На конкретном `ProjectController` прежние `Load`, `ImportMesh`, `ImportCAD` и `CreateProject`
временно оставлены как совместимые адаптеры для существующих клиентов. Они вызывают новые
операции, но не входят в `IProjectController`. Адаптер `ImportMesh` сохраняет прежний смысл
«открыть файл как сетку», в том числе для `.bpf` и `.bpf2`; общий `Open` для этих расширений
открывает полный проект. `Append(string)` остаётся частью нового контракта с необязательным
параметром прогресса и возвращает `void`: изменения наборов и групп клиент получает через
`Message`. Загрузчик модели выбирается в `ModelLoaderFactory` по расширению. При неподдерживаемом
расширении `Open` и `Append` завершаются исключением, не меняя текущий проект.

Свойства `HasProject`, `FilePath`, `IsModified` доступны для чтения. `IsModified` отмечает
несохранённые изменения и сбрасывается после открытия, создания или сохранения. Отдельных
`StateChanged` и `IsBusy` в контракте нет. Изменение одного только `IsModified` не вызывает
`Message`; доступность команд клиент определяет по текущему состоянию.

`progress` необязателен. `Open` сообщает процент при чтении проектов `.bpf` и `.bpf2`.
`Open` для сеточных форматов и `Append` передают процент от загрузчиков текстовых сеточных
форматов (`.inp`, `.inp_v2`, `.asc`, `.dat`, `.cdb` и текстовый STL) по числу строк, а от
загрузчика бинарного STL — по числу байт. Значение не убывает и достигает 100 после проходов
чтения файла; для `.bpf` и `.bpf2` учитываются проходы чтения модели и данных задачи, без сброса
процента между ними. Разбор оставшихся данных и обновление контроллера могут продолжаться после
100, поэтому индикатор занятости GUI остаётся до завершения команды.

### 2.3. Единственная точка замены

`Open(path)` выбирает загрузку по расширению: `.bpf` и `.bpf2` читает как полный проект,
остальные поддерживаемые форматы — как сеточную модель. После успешного чтения контроллер
готовит `ModelView` для новой модели, вызывает `Replace` и публикует один
`Message(ProjectChange.Loaded)`. Для сеточного формата `Open` создаёт новый проект с прочитанной
моделью. `Create`, `ImportGeometry` и `Close` также передают в `Replace` соответствующий вид
изменения.
`Publish(change)` создаёт `ProjectMessageEventArgs` для всех вариантов изменений.

`MarkModelSurfaces` получает модель параметром, чтобы обработать новую модель до замены текущего
проекта. Текстовые `LoadEvent` загрузчика не транслируются в контроллер; процент чтения
передаётся отдельно от них.

`Open` для сеточного формата и `Append` берут загрузчик из
`ModelLoaderFactory.Create(extension)`.

### 2.4. Импорт геометрии

Импорт CAD меняет глобальное состояние Gmsh (`Gmsh.Clear()`, `Open`), подготовить его в стороне
нельзя. Поэтому `ImportGeometry`:

1. выполняется без параллельного чтения или изменения данных контроллера: это обеспечивает клиент;
2. собирает новый `ProjectData` в локальной переменной и только в конце вызывает `Replace`;
3. при ошибке вызывает `Replace` с пустым проектом (`Closed`) и пробрасывает исключение: прежнюю
   геометрию в Gmsh уже не вернуть, а оставить старый `ProjectData` поверх очищенного Gmsh — значит
   показать пользователю несуществующую геометрию.

Клиент исключает параллельные команды контроллера, включая `Open`, `Append`,
`GenerateMesh`, `RefineMesh` и `ExtrudeElement*`. Контроллер сам не обеспечивает
потокобезопасность: `BusyScope`, `BeginBusy` и `IsBusy` отсутствуют.

`InitializeGeometry` вызывается один раз при старте приложения.

### 2.5. Изменения данных — `IProjectEvents.Message`

`ProjectMessageEventArgs.Change` содержит ровно один из пяти вариантов `ChangeMessage`:

| Вариант | Данные и назначение |
| --- | --- |
| `GeoChange` | Снимок `Counts : IReadOnlyDictionary<GeometryEntityKind, int>`: число точек, кривых, поверхностей и объёмов в CAD после синхронизации с внутренними данными. Все четыре вида присутствуют, включая нулевые значения. Отдельный `GeometryEntityKind` нужен, поскольку в `ObjType` нет объёма. Событие публикуется после изменения геометрии, даже если количества остались прежними. |
| `MeshChange` | `DataKind = Set / Group`, `Action = Created / Updated / Deleted`, `ObjectType`, `EntityId`. Последнее поле — устойчивый `Number` набора или группы. Ключ внутри проекта: `DataKind + ObjectType + EntityId`. Изменение состава набора после удаления узла относится сюда. |
| `CondChange` | Вид условия (`DataKind`: нагрузка, закрепление, нагрев, среда, материал), `Action` и `Id` — индекс в списке условий. При удалении это индекс непосредственно до удаления, при создании и изменении — текущий индекс. При отложенной обработке GUI перечитывает список целиком: индексы могли сдвинуться. |
| `ViewChange` | `ChangeKind`, `AffectedSets` и `GetChangeKind(setInfo)` для отдельных наборов. Контроллер преобразует `ModelView.Changed` в `Message(ViewChange)`. |
| `ProjectChange` | `ChangeKind = Loaded / Created / Closed / PropertyChanged`. Только при `PropertyChanged` заполнено `Property`: `Name`, `FilePath`, `TaskKind`, `TaskType`, `MaterialsDB` или `FunctionsDB`. |

При загрузке, создании и закрытии проекта GUI полностью обновляет представление по одному
`ProjectChange`; отдельные события для каждого объекта не нужны. Команды изменения геометрии,
наборов, групп, условий и свойств проекта публикуют соответствующий `Message` после каждого
согласованного шага. Если операция меняет несколько сущностей, сообщения приходят
последовательно по мере её выполнения. Накопителя и `BeginUpdate` у событий проекта нет.
Изменённое условие клиент передаёт в `UpdateCondition(index, condition)`; прямое изменение свойств
объекта, полученного через запрос, контроллер обнаружить не может и событие не публикует.
Если смена `TaskKind` или `TaskType` очищает условия, после соответствующего изменения
публикуются отдельные `CondChange`.

Запросы и экспорт (`ExportMesh`, `ExportGeometry`, `SaveSMF`, `CopyFile`) данные проекта не меняют.
Выборки `SelectNodeInDirection`, `SelectNodeInPlane`, `SelectE2DInPlane`, если меняют выделение
через `ModelView`, приводят к `ViewChange`. Установка общих параметров генерации сетки
(`SetMeshMinimumSize`, `SetMeshMaximumSize`, `SetMeshAlgorithm2D`, `SetMeshAlgorithm3D`,
`SetMeshSizeFactor`), параметров отдельных геометрических объектов (`SetCurveMeshingSettings`,
`SetSurfaceMeshingSettings`, `SetVolumeMeshingSettings`, `SetMeshPointSize`,
`SetEmbeddedGeometryEntities`) и загрузка настроек через `LoadSMF` не вызывают `Message`.
Последующие операции, изменяющие геометрию или сеточные данные, публикуют соответствующие
события по общим правилам.

### 2.6. Замена внутреннего ModelView

- `ModelView` не публикуется ни как конкретный тип, ни как `IModelView`. Публичные запросы и
  команды представления находятся на `IProjectController` в едином `IProjectView`:
  настройки вида читаются через запросы и меняются командами
  `SetSelectionColor`, `SetTransparency`, `SetHideInsideSurfaces`; там же доступны цвета объектов,
  видимость, выделение и пакет изменений (`BeginViewUpdate`). Контроллер делегирует их текущему
  `ModelView`; интерфейсы не возвращают ссылку на него или его `Model`.
- `Replace` считывает из прежнего представления `SelectionColor`, `Transparency` и
  `HideInsideSurfaces`, создаёт `ModelView` для новой `ModelData` и переносит эти три настройки.
  Выделение, скрытость, индивидуальные цвета, стили наборов и накопитель `changedSets` в новый
  экземпляр не переходят.
- Контроллер снимает свою подписку на `Changed` со старого экземпляра и подписывается на новый.
  Новый экземпляр не создаётся в геттере. Перенос настроек не публикует `ViewChange`: после
  замены данных публикуется один `Message(ProjectChange)`, по которому клиент перестраивает GUI.
- Замена проекта не выполняется внутри открытого `BeginViewUpdate`; пакет нужно завершить до
  вызова `Open`, `Create`, `ImportGeometry` или `Close`.
- `Append` не заменяет модель и её представление: выделение и скрытость сохраняются.

### 2.7. Сообщения

- `Message : EventHandler<ProjectMessageEventArgs>` передаёт `ChangeMessage` напрямую
  потребителям. Каждый подписчик управляет своей подпиской (`+=` / `-=`).
- `Message` не передаёт процент чтения или строки статуса; у `ProjectMessageEventArgs` нет `Text`
  и `Level`. Процент идёт только в `IProgress<int>` конкретного вызова чтения. Оболочка включает
  и выключает собственный индикатор занятости вокруг всей команды.
- Ошибка операции передаётся исключением, а не строкой статуса.
- Диагностика `MarkModelSurfaces` при грани, принадлежащей более чем двум элементам, оформляется
  как `InvalidDataException` с номерами элементов. При ошибке чтения текущий проект сохраняется;
  диагностика не маскируется строкой статуса или `ChangeMessage`.

### 2.8. Препроцессор

Формирование расчётных инструкций принадлежит `PreProc`, а не `ProjectController`.
В BazisGUI обработчик меню «Расчёты / Сформировать» получает `TaskKind` и условия
из контроллера, создаёт `ProcessProperty`, затем вызывает `IPreProc.CalcCompDataV2`
и `IPreProc.SortCompDataByTimeAndType`. Интерфейс `IComputationCommands` и зависимость
`OperationalController → PreProc` не нужны.

## 3. Как этим пользуется оболочка

```csharp
// открыть проект
// оболочка блокирует команды проекта, но продолжает обрабатывать сообщения UI
var progress = new Progress<int>(percent => progressBar.Value = percent);
await Task.Run(() => project.Open(path, progress));

// импорт CAD: клиент исключает параллельное чтение и изменение контроллера
project.ImportGeometry(path);
```

- Корень композиции создаёт `ProjectController` один раз, вызывает
  `InitializeGeometry` один раз и раздаёт ссылки.
- Корневое окно Gerbera хранит `IProjectController`, подписывается на его `Message` и снимает
  подписку при закрытии. Обработчик переносит уведомление в UI-поток и обновляет сцену и
  навигатор. Данные читаются через тот же интерфейс; команды представления вызываются на
  контроллере, без доступа к `ModelView`.
- Оболочка показывает статус и занятость из контекста запущенной команды и снимает индикатор
  после её завершения, в том числе при исключении. Если загрузчик поддерживает процент чтения,
  оболочка показывает и его; в остальных случаях использует неопределённый индикатор.
  `ProjectController.Message` передаёт только изменения данных, без текстового журнала.
- `Progress<int>` создаётся в UI-потоке и доставляет процент через его `SynchronizationContext`.
  Если заблокировать сам UI-поток синхронным ожиданием, индикатор не обновится до завершения
  загрузки. Поэтому оболочка отключает команды на время работы фонового потока, сохраняя цикл UI.
- Контроллер поднимает события в потоке, где выполнялась операция. Оболочка переносит обработку
  в UI-поток.
- Gerbera хранит один экземпляр `IProjectController`. Открытие и добавление файлов выполняются
  через `Open` и `Append`; настройки и изменение вида передаются через `IProjectView`.

## 4. Риски интеграции

- **Пропущенное событие.** Среди команд изменения данных есть операции с каскадным эффектом;
  пропуск события оставит GUI с устаревшими данными. Нужны тесты по группам таких команд на вид
  `ChangeMessage`, действие и адрес сущности. Команды настройки генерации сетки и изменение одного
  только `IsModified` события не требуют.
- **Потоки.** Контроллер не потокобезопасен. Клиент исключает параллельное чтение и изменение;
  события возникают в потоке выполняемой операции, поэтому GUI переносит обработку в UI-поток.
- **Ошибка импорта геометрии закрывает проект.** Альтернативы при глобальном Gmsh нет.
